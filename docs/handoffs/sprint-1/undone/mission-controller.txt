THE WHOLE SYSTEM, IN ONE PAGE — read this first
───────────────────────────────────────────────

DroneDeck flies a Crazyflie around a room, stops at pieces of equipment, and
records temperature, pressure and camera frames at each. It has three parts:

  1  PLANNING — "what to fly"                           Samuel · built
     In the desktop app (Auto › Control › ① Mission) the operator draws a
     ROOM: a closed geofence and the obstacles inside it. Then a MISSION in
     that room: a HOME mark where the drone sits before takeoff, and an
     ordered list of INSPECTION POINTS, each an (x, y) position, a height and
     a hold time. The agent checks every point and every straight line
     between them against the fence and the obstacles, and saves the mission
     as a JSON file on the laptop.

  2  FLYING — "how it is flown"                         Hannah · YOUR PART
     The operator runs the checks (② Check) and presses Start mission
     (③ Fly). The session refuses anything unsafe BEFORE a motor turns, then
     arms the MANUAL FLIGHT SYSTEM — the tuned 50 Hz loop that flies Manual
     mode — and hands it, with the mission, to the MISSION CONTROLLER. The
     mission controller flies the mission by giving that system goals, one
     inspection point at a time.

  3  PROCESSING — "what the readings say"               Samuel, Kevin, Reagan
     Every reading and camera frame taken while the drone HOLDS at a point is
     stamped with that point's id. After the flight (and later, during it),
     the data pipeline cleans the readings, enhances the frames, classifies
     both, and gives every inspection point a verdict.

WHAT A MISSION IS
─────────────────

A mission is DATA — a plan, never code. It arrives already validated.

  backend/agent/cropwatcher/mission/plan/mission.py

  InspectionPoint                 one place the drone must hold and record
    id: str                       stable, unique within the mission ("P1"). Every
                                  reading taken there is stamped with it, so it
                                  never changes once saved.
    x_m, y_m: float               absolute Lighthouse metres — the room's frame,
                                  exactly what the estimator reports
    z_m: float                    metres ABOVE THE FLOOR captured at takeoff
                                  (CLAUDE.md invariant 4)
    hold_s: float                 at least 5.0 (story 3.4)
    label: str | None             "Pump 2"

  Mission
    id, name, room_id             which room's geofence and obstacles apply
    home: (x, y)                  WHERE THE DRONE IS at Start (see below)
    points: tuple[InspectionPoint, ...]   at least one, IN FLYING ORDER —
                                  exactly the points to fly
    cruise_height_m: float        the height to take off to
    return_to_start: bool         fly back over home (the real start) first
    end_point_id: None            always None by the time you see it
    revision: int                 which version of the plan this is

  CHANGED 2026-09-29 — THE MISSION YOU ARE HANDED IS THE MISSION AS FLOWN
  (Mission.from_start). The session replaces the saved plan's planned start
  with the drone's own position, drops any points after the operator's END
  POINT (and turns return_to_start off when there is one), and re-validates
  that. So: fly `points` in order, honour `return_to_start`, and read
  nothing else — no end point or planned start to interpret. Nothing in your
  interface (__init__, start, abort, state, completed_point_ids,
  current_point_id) changed.

BY THE TIME A MISSION REACHES YOU, THE SESSION HAS ALREADY CHECKED
(session.py run_mission, before anything arms):
  - every inspection point and home (the drone's spot) are inside the room's
    geofence, clear of its edge and of every obstacle by the room's
    clearance (0.25 m default);
  - every leg — home → P1 → … → last point (→ home) — stays inside the fence
    and clear of every obstacle, even in an L-shaped room, FROM WHERE THE
    DRONE ACTUALLY IS;
  - every height is inside the room's height band, every hold ≥ 5 s;
  - the battery covers that path's estimated time;
  - the checks passed and the operator confirmed the area; Auto; assisted.
Do not re-validate the plan. Do keep the in-flight rules below: a valid plan
can still meet a room that changed.


HOW THE MISSION CONTROLLER TAKES IT
───────────────────────────────────

The session builds it and starts it (session.py _do_mission):

  controller = link.manual(report)          # the manual flight system
  controller.arm(); controller.start()      # props idling, 50 Hz loop running
  flying = MissionController(mission, controller, on_event=self._on_mission_event)
  flying.start()                            # YOUR code from here on

The session also: starts the in-flight guard with THE ROOM'S OWN GEOFENCE as
its fence (it lands the drone if the drone leaves it), records the flight CSV
and trace, keeps a copy of the plan flown, reads your current_point_id on every
row and frame, publishes your events to the app, and — when the flight comes
down for any reason — calls your abort("the flight ended") if you are not
already in a terminal state.

WHAT IT EXECUTES THE MISSION WITH
─────────────────────────────────

The manual flight system — flight/manual.py ManualController — the same code
that flies Manual mode, tuned and tested. You see it only through MissionFlight
(mission/controller/flight.py):

  state -> ControlState           idle | armed | flying | landing | landed | stopped
  assisted -> bool                True only with a Lighthouse position
  target -> Fix | None            the commanded point (x, y, yaw_deg)
  target_height -> float          the commanded height above the floor
  drift_m -> float                how far the drone is from the commanded point
  goal_active -> bool             True while gliding towards a hold_at/fly_to goal
  operator_override -> bool       True once a held key cancelled a goal

  hold_at(height_m)               rise to a height and hold it (takeoff)
  fly_to(x, y, height_m)          glide the commanded point to (x, y, height) in
                                  a straight line, and hold it there
  land()                          land where it is

fly_to() ADDS NO CONTROL LAW (manual.py, its docstring). It moves the one
commanded point the manual system always flies, at the arrow keys' eased speed
(0.20 m/s), on the same 30 cm leash, slowing before the goal so it arrives
instead of overshooting. Any held key cancels it and sets operator_override.
That is why a mission inherits everything tuned into manual flight — and why
YOUR CONTROLLER DECIDES WHERE NEXT AND WHEN, AND NEVER HOW.

Do NOT call arm(), start(), stop(), emergency_stop() or heartbeat(). The session
owns arming and stopping. THE HEARTBEAT STAYS WITH THE DESKTOP APP ON PURPOSE:
if the operator's window goes quiet, the drone lands, mission or not. That is
the dead-man, and a mission must never defeat it.


WHAT YOU BUILD
──────────────

The body of mission/controller/mission_controller.py. Its interface is fixed
(the session, the app and the pipeline depend on it); today every method is a
placeholder and BUILT = False, which makes the session refuse to arm a mission.

  class MissionController:
      BUILT = False                           # set True when your body lands
      def __init__(self, mission, flight: MissionFlight, *,
                   on_event: Callable[[MissionEvent], None],
                   clock: Callable[[], float] = time.monotonic,
                   tick_s: float = 0.1): ...
      def start(self) -> None                 # run tick() on its own thread, 10 Hz
      def tick(self) -> None                  # ONE step; tests drive it with a fake clock
      def abort(self, reason: str) -> None    # land now; ABORTED. Safe to call twice
      state -> MissionState
      current_point_id -> str | None
      completed_point_ids -> tuple[str, ...]

States and events are in mission/controller/events.py (fixed):

  MissionState   idle → taking_off → (transit → arriving → holding)×N
                 → returning → landing → done
                 terminal: done | aborted | interrupted | failed
  EventKind      started, takeoff_done, point_arrived, hold_started,
                 point_complete, returning, landed, done, aborted,
                 interrupted, failed
  MissionEvent   kind, at_s (your clock), point_id, detail (a sentence the
                 operator reads: "P2 reached, 4 cm off")

current_point_id — THE CONTRACT WITH DATA COLLECTION
  - Set ONLY while HOLDING; None in every other state (takeoff, transit,
    arriving, returning, landing). Readings taken while moving must not carry
    a point id — the pipeline would analyse them as the equipment.
  - Read from other threads, at 10 Hz, at any moment: it must be safe to.

EVENTS — THE CONTRACT WITH THE APP AND THE PIPELINE
  - Call on_event OUTSIDE any lock. An exception it raises is logged and
    swallowed: a broken listener must never stop a mission in the air.
  - In order, and exactly one terminal event per mission.
  - POINT_COMPLETE is what the live pipeline will listen for.


THE RULES THE STATE MACHINE MUST FOLLOW
───────────────────────────────────────

 1. ASSISTED ONLY. start() raises MissionError when flight.assisted is False.

 2. TAKEOFF: hold_at(mission.cruise_height_m), then wait until goal_active is
    False and the state is "flying". Record the takeoff x, y (flight.target).

 3. EACH POINT: fly_to(point.x_m, point.y_m, point.z_m), then
    ARRIVAL = goal_active is False (the commanded point is there) AND
    drift_m ≤ ARRIVE_M (the drone is there too), continuously for SETTLE_S.
    Drift back over ARRIVE_M restarts the settle timer.
    HOLD for point.hold_s, timed from when the hold starts.

 4. TIMEOUTS LAND THE DRONE. Transit longer than
    leg length / 0.20 m/s + TRANSIT_MARGIN_S, or arrival longer than
    SETTLE_TIMEOUT_S: land(), ABORTED, the reason in the event. Never skip a
    point and carry on.

 5. WATCH THE FLIGHT EVERY TICK:
    - operator_override becomes True: stop commanding at once, INTERRUPTED.
      The operator has the drone, as in Manual. Do not land for them.
    - state becomes landing, landed, stopped or idle when you did not ask:
      a guard, the dead-man or an emergency stop ended it. ABORTED, with that
      state in the reason. Never call land() after "stopped".

 6. NO BATTERY THRESHOLD OF YOUR OWN. The guard lands on low battery; rule 5
    turns that into ABORTED (CLAUDE.md invariant 1).

 7. RETURN AND LAND: if return_to_start, fly_to the takeoff x, y at cruise
    height, then land(). DONE once the state is "landed".

 8. THREADING: your own thread at 10 Hz; ManualController keeps its own 50 Hz
    loop, untouched. Never sleep while holding a lock. Public methods are
    thread-safe. start() twice raises; abort() twice is harmless.

 9. THE STARTING CONSTANTS ARE GUESSES until the lab measures them — each is
    replaced by the measured value with the flight trace cited beside it:
      ARRIVE_M = 0.10   SETTLE_S = 1.0   SETTLE_TIMEOUT_S = 10.0
      TRANSIT_MARGIN_S = 5.0            (mission_controller.py)

REQUIRED TESTS (tests/mission/test_controller.py):

  [ ] Each hold lasts at least hold_s; current_point_id is set only while

  [ ] An exception in on_event does not stop the mission.
  [ ] Refuses to start unassisted; start() twice raises; abort() twice is fine.
  [ ] Exactly one terminal event, in every scenario above.
