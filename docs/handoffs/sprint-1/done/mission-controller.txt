THE WHOLE SYSTEM, IN ONE PAGE — read this first (Yordi too)
───────────────────────────────────────────────────────────

DroneDeck flies a Crazyflie around a room, stops at pieces of equipment, and
records temperature, pressure and camera frames at each. It has three parts:

  1  PLANNING — "what to fly"                           Samuel · built
     In the desktop app (Auto › Control › ① Mission) the operator draws a
     ROOM: a closed geofence and the obstacles inside it. Then a MISSION in
     that room: an ordered list of INSPECTION POINTS, each an (x, y)
     position, a height and a hold time. The agent checks every point and
     every straight line between them against the fence and the obstacles,
     and saves the mission as a JSON file on the laptop.

  2  FLYING — "how it is flown"                         Hannah + Yordi
     The operator runs the checks (② Check) and presses Start mission
     (③ Fly). The session refuses anything unsafe BEFORE a motor turns, then
     arms the MANUAL FLIGHT SYSTEM — the tuned 50 Hz loop that flies Manual
     mode — and hands it, with the mission, to the MISSION CONTROLLER. The
     mission controller flies the mission by giving that system goals, one
     inspection point at a time. Hannah builds the controller; Yordi proves
     it, in simulation and then on the drone.

  3  PROCESSING — "what the readings say"               Samuel, Kevin, Reagan
     Every reading and camera frame taken while the drone HOLDS at a point is
     stamped with that point's id. After the flight (and later, during it),
     the data pipeline cleans the readings, enhances the frames, classifies
     both, and gives every inspection point a verdict.

WHAT A MISSION IS
─────────────────

A mission is DATA — a plan, never code. It arrives already validated.

  backend/agent/cropwatcher/mission/plan/mission.py

  InspectionPoint                 one place the drone must hold and record
    id: str                       stable, unique within the mission ("P1"). Every
                                  reading taken there is stamped with it, so it
                                  never changes once saved.
    x_m, y_m: float               absolute Lighthouse metres — the room's frame,
                                  exactly what the estimator reports
    z_m: float                    metres ABOVE THE FLOOR captured at takeoff
                                  (CLAUDE.md invariant 4)
    hold_s: float                 at least 5.0 (story 3.4)
    label: str | None             "Pump 2"

  Mission
    id, name, room_id             which room's geofence and obstacles apply
    home: (x, y)                  WHERE THE DRONE IS at Start
    points: tuple[InspectionPoint, ...]   at least one, IN FLYING ORDER —
                                  exactly the points to fly
    cruise_height_m: float        the height to take off to
    return_to_start: bool         fly back over the takeoff spot first
    end_point_id: None            always None by the time you see it
    revision: int                 which version of the plan this is

  THE MISSION YOU ARE HANDED IS THE MISSION AS FLOWN (Mission.from_start).
  The session replaces the saved plan's planned start with the drone's own
  position, drops any points after the operator's END POINT (and turns
  return_to_start off when there is one), and re-validates that. So: fly
  `points` in order, honour `return_to_start`, and read nothing else — no
  end point or planned start to interpret.

BY THE TIME A MISSION REACHES YOU, THE SESSION HAS ALREADY CHECKED
(session.py run_mission, before anything arms):
  - every inspection point and the drone's spot are inside the room's
    geofence, clear of its edge and of every obstacle by the room's
    clearance (0.25 m default);
  - every leg — start → P1 → … → last point (→ start) — stays inside the
    fence and clear of every obstacle, even in an L-shaped room, FROM WHERE
    THE DRONE ACTUALLY IS;
  - every height is inside the room's height band, every hold ≥ 5 s;
  - the battery covers that path's estimated time;
  - the checks passed and the operator confirmed the area; Auto; assisted.
Do not re-validate the plan. Do keep the in-flight rules below: a valid plan
can still meet a room that changed.


HOW THE MISSION CONTROLLER TAKES IT
───────────────────────────────────

The session builds it and starts it (session.py _do_mission):

  controller = link.manual(report)          # the manual flight system
  controller.arm(); controller.start()      # props idling, 50 Hz loop running
  flying = MissionController(mission, controller, on_event=self._on_mission_event)
  flying.start()                            # YOUR code from here on

The session also: starts the in-flight guard with THE ROOM'S OWN GEOFENCE as
its fence (it lands the drone if the drone leaves it), records the flight CSV
and trace, keeps a copy of the plan flown, reads your current_point_id on every
row and frame, publishes your events to the app, and — when the flight comes
down for any reason — calls your abort("the flight ended") if you are not
already in a terminal state.


WHAT IT EXECUTES THE MISSION WITH
─────────────────────────────────

The manual flight system — flight/manual.py ManualController — the same code
that flies Manual mode, tuned and tested. You see it only through MissionFlight
(mission/controller/flight.py):

  state -> ControlState           idle | armed | flying | landing | landed | stopped
  assisted -> bool                True only with a Lighthouse position
  target -> Fix | None            the commanded point (x, y, yaw_deg)
  target_height -> float          the commanded height above the floor
  drift_m -> float                how far the drone is from the commanded point
  goal_active -> bool             True while gliding towards a hold_at/fly_to goal
  operator_override -> bool       True once a held key cancelled a goal

  hold_at(height_m)               rise to a height and hold it (takeoff)
  fly_to(x, y, height_m)          glide the commanded point to (x, y, height) in
                                  a straight line, and hold it there
  land()                          land where it is

fly_to() ADDS NO CONTROL LAW (manual.py, its docstring). It moves the one
commanded point the manual system always flies, at the arrow keys' eased speed
(MOVE_SPEED_M_S, 0.20 m/s), on the same 30 cm leash, slowing before the goal
so it arrives instead of overshooting. Any held key cancels it and sets
operator_override. That is why a mission inherits everything tuned into manual
flight — and why YOUR CONTROLLER DECIDES WHERE NEXT AND WHEN, AND NEVER HOW.

Do NOT call arm(), start(), stop(), emergency_stop() or heartbeat(). The session
owns arming and stopping. THE HEARTBEAT STAYS WITH THE DESKTOP APP ON PURPOSE:
if the operator's window goes quiet, the drone lands, mission or not. That is
the dead-man, and a mission must never defeat it.


WHAT YOU BUILD
──────────────

The body of mission/controller/mission_controller.py. Its interface is fixed
(the session, the app and the pipeline depend on it); today every method is a
placeholder and BUILT = False, which makes the session refuse to arm a mission.

  class MissionController:
      BUILT = False                           # True when your body lands
      def __init__(self, mission, flight: MissionFlight, *,
                   on_event: Callable[[MissionEvent], None],
                   clock: Callable[[], float] = time.monotonic,
                   tick_s: float = 0.1): ...
      def start(self) -> None                 # checks, takeoff, then the thread
      def tick(self) -> None                  # ONE step; tests call it directly
      def abort(self, reason: str) -> None    # land now; ABORTED. Safe twice
      state -> MissionState
      current_point_id -> str | None
      completed_point_ids -> tuple[str, ...]

States and events are in mission/controller/events.py (fixed):

  MissionState   idle → taking_off → (transit → arriving → holding)×N
                 → returning → landing → done
                 terminal: done | aborted | interrupted | failed
  EventKind      started, takeoff_done, point_arrived, hold_started,
                 point_complete, returning, landed, done, aborted,
                 interrupted, failed
  MissionEvent   kind, at_s (your clock), point_id, detail (a sentence the
                 operator reads: "P2 reached, 4 cm off")


THE SPEC — what the controller does (Hannah builds it, Yordi checks it)
───────────────────────────────────────────────────────────────────────

Anything the two of you settle later is added HERE, dated, in the same pull
request that relies on it.

STARTING
 S1. start() raises MissionError, and commands nothing and emits nothing,
     when flight.assisted is False, or when start() was already called.
 S2. Otherwise start(), before it returns: emits STARTED, calls
     hold_at(mission.cruise_height_m), and the state is TAKING_OFF. Then,
     when tick_s > 0, it starts the controller's own thread, which calls
     tick() every tick_s seconds; when tick_s == 0 it starts no thread and
     the caller calls tick() (HOW THE TWO HALVES MEET, 3).

ONE TICK — checked in this order, and the first that applies ends the tick
 T1. In a terminal state: do nothing.
 T2. flight.operator_override is True: stop commanding at once — no fly_to,
     no hold_at, no land(), now or later. INTERRUPTED. The operator has the
     drone, as in Manual; do not land for them.
 T3. flight.state is landing, landed, stopped or idle and the controller
     did not call land(): a guard, the dead-man or an emergency stop ended
     the flight. ABORTED, with that state named in the detail. Do not call
     land() — the flight is already coming down or stopped.
 T4. A timeout (T8, T10) has run out: call land() (unless the state is
     stopped), then ABORTED, with what timed out in the detail.
 T5. Otherwise, the step for the current state (below).
 Any exception raised inside tick(): call land() if the flight state is
 flying, then FAILED with the exception's message. It never escapes the
 thread and never stops the manual system's own loop.

TAKEOFF
 T6. TAKING_OFF ends when goal_active is False AND flight.state is flying.
     Record the takeoff spot: flight.target's x, y. Emit TAKEOFF_DONE and
     begin the first point.
 T7. Takeoff has a timeout, like a leg: cruise_height_m / CLIMB_RATE_M_S +
     TRANSIT_MARGIN_S, from start(). (Added in the split: without it a
     drone that never rises waits forever.)

EACH POINT, in order
 T8. TRANSIT: call fly_to(point.x_m, point.y_m, point.z_m) once, on
     entering. The leg is the straight 3-D distance from the commanded spot
     it starts from (the takeoff spot at cruise height, or the last point)
     to this point. Transit times out after
     leg / MOVE_SPEED_M_S + TRANSIT_MARGIN_S, from the fly_to call.
     Transit ends when goal_active is False: emit POINT_ARRIVED (point_id
     set, detail "P2 reached, 4 cm off" with the drift then) → ARRIVING.
 T9. ARRIVING: arrival is drift_m ≤ ARRIVE_M continuously for SETTLE_S.
     Drift back over ARRIVE_M restarts that SETTLE_S wait.
 T10. ARRIVING times out SETTLE_TIMEOUT_S after it began — a timeout that
     drift does NOT restart.
 T11. Settled: set current_point_id, THEN emit HOLD_STARTED → HOLDING.
 T12. HOLDING lasts point.hold_s from HOLD_STARTED, by `clock`. Drift while
     holding neither restarts nor ends the hold (the trace records it, the
     guard handles anything dangerous).
 T13. Hold done: clear current_point_id, add the id to
     completed_point_ids, THEN emit POINT_COMPLETE — then the next point,
     or the end. NEVER SKIP A POINT: a point that cannot be reached ends the
     mission (T4); it is never left out while the rest are flown.

THE END
 T14. return_to_start: emit RETURNING → RETURNING, fly_to(the takeoff x, y,
     cruise_height_m), with T8's timeout and T9–T10's settle; once settled,
     land() → LANDING. Without return_to_start: land() right after the last
     POINT_COMPLETE → LANDING (there is no RETURNING event).
 T15. LANDING: flight.state landed → emit LANDED, then DONE. flight.state
     stopped or idle before landed → ABORTED, the state in the detail.

ABORT, CALLED FROM OUTSIDE (the session)
 A1. abort(reason) in a terminal state: nothing — no command, no event.
 A2. Otherwise: land() if flight.state is flying or armed, never when it is
     stopped, landing or landed; then ABORTED with `reason` as the detail.

EVENTS — the contract with the app and the pipeline
 E1. Exactly ONE terminal event (DONE, ABORTED, INTERRUPTED, FAILED) per
     mission, and it is the LAST event — nothing is emitted after it.
 E2. The state becomes terminal in the same step its event is emitted.
 E3. point_id is the point's id on POINT_ARRIVED, HOLD_STARTED,
     POINT_COMPLETE, and on a terminal event that ends a point (transit,
     arriving or holding); None on every other event.
 E4. at_s is `clock()` at the moment of the step that emitted it.
 E5. on_event is called OUTSIDE any lock. An exception it raises is logged
     (logging.getLogger(__name__)) and swallowed: a broken listener must
     never stop a mission in the air.
 E6. Tests check an event's kind, point_id and order — and, in a detail,
     only that it NAMES the cause (the state, "timed out", the reason). The
     wording of a detail is Hannah's to choose; no test pins it.

A 3-point mission with return_to_start emits exactly:
    STARTED · TAKEOFF_DONE ·
    POINT_ARRIVED P1 · HOLD_STARTED P1 · POINT_COMPLETE P1 ·
    POINT_ARRIVED P2 · HOLD_STARTED P2 · POINT_COMPLETE P2 ·
    POINT_ARRIVED P3 · HOLD_STARTED P3 · POINT_COMPLETE P3 ·
    RETURNING · LANDED · DONE
and, without return_to_start, the same with RETURNING left out.

current_point_id — THE CONTRACT WITH DATA COLLECTION
 C1. Set ONLY while HOLDING; None in every other state (takeoff, transit,
     arriving, returning, landing, and every terminal state). A reading
     taken while moving must not carry a point id — the pipeline would
     analyse it as the equipment.
 C2. Read from other threads, at 10 Hz, at any moment: it must be safe to.

THREADING
 R1. The controller's thread at tick_s; ManualController keeps its own
     50 Hz loop, untouched. Never sleep while holding a lock. Public methods
     are thread-safe; start() twice raises (S1); abort() twice is harmless.

NO BATTERY THRESHOLD OF YOUR OWN
 R2. The guard lands on low battery; T3 turns that into ABORTED (CLAUDE.md
     flight invariant 1).

THE STARTING CONSTANTS ARE GUESSES until the lab measures them (Yordi's
ticket). Keep them as named module constants in mission_controller.py:
      ARRIVE_M = 0.10   SETTLE_S = 1.0   SETTLE_TIMEOUT_S = 10.0
      TRANSIT_MARGIN_S = 5.0
