PART 1 — THE SIMULATED DRONE  (tests/sim_drone.py; lands first, step a)
───────────────────────────────────────────────────────────────────────

A drone in software that the REAL manual flight system flies. Not a mock of
ManualController — the real one, so every scenario proves the controller AND
the tuned flight system together. tests/test_manual.py's Rig and
TestFlyTo show the pattern it grows out of: a ManualController over a
FakeCommander and a FakeClock, whose `position` callback is what the
estimator "reports".

WHAT IT MUST OFFER — the shape both of you rely on. Names may improve in
your pre-flight; if they do, tell Hannah and write the change here.

  MANUAL_TICK_S = flight.manual.TICK_S      # 0.02 — the 50 Hz loop
  MISSION_TICK_S = 0.1                      # how often it ticks a mission

  class SimDrone:
      def __init__(self, *, start: Fix, ground_z: float = 1.0,
                   assisted: bool = True, lag_s: float = 0.5,
                   noise_m: float = 0.0, drift_m_s: tuple[float, float] = (0, 0),
                   seed: int = 0) -> None
      clock: FakeClock                      # the ONE clock of a scenario
      cmd: FakeCommander                    # every command the drone got
      ctl: ManualController                 # real; satisfies MissionFlight
      position: Fix                         # what the estimator reports now
      def arm(self) -> None                 # what the session does: arm + start
      def step(self, seconds: float, mission=None) -> None
          # advance the clock in MANUAL_TICK_S steps: heartbeat (unless the
          # window has gone quiet), ctl.tick(), move the drone; and call
          # mission.tick() every MISSION_TICK_S when a mission is given
      def run_until(self, mission, done, *, limit_s: float) -> float
          # step until done() is true; fail the test at limit_s — no
          # scenario can hang
      # the things that go wrong, each a real path the flight system has:
      def stall(self) -> None               # stops following: a stuck drone
      def push(self, dx: float, dy: float) -> None   # a gust, at a believable
                                            # speed (the Rig's drift(): the
                                            # loop rejects estimator jumps)
      def hold_key(self, intent: Intent) -> None     # the operator takes over
      def guard_lands(self) -> None         # what the in-flight guard does
      def emergency_stop(self) -> None
      def window_goes_quiet(self) -> None   # heartbeats stop: the dead-man
      landed_at: tuple[float, float] | None # where it touched down

HOW IT MOVES. The reported position follows the last POSITION setpoint the
drone was sent with a first-order lag (time constant lag_s — about 0.5 s is
a starting guess; after the lab, set it from the traces), plus optional
Gaussian noise (seeded — every run the same) and a steady drift.

ITS OWN TESTS (tests/test_sim_drone.py) — the simulator is code, and a
simulator that is wrong makes every scenario lie:
  [ ] it follows a fly_to() goal, and arrives within 1 cm with no noise;
  [ ] the lag: after a step in the commanded point it covers ~63 % of it in
      lag_s;
  [ ] the same seed gives the same flight, byte for byte;
  [ ] stall(): the commanded point moves on and the drone does not — the
      30 cm leash holds the commanded point back (manual.py LEASH_M);
  [ ] hold_key() cancels a goal and sets operator_override;
  [ ] guard_lands(), emergency_stop(), window_goes_quiet() each put ctl in
      the state the real system reaches (landing, stopped, landing).


PART 2 — THE MISSION REPORT  (cropwatcher/mission/review.py + CLI)
──────────────────────────────────────────────────────────────────

Production code, for the operator and for the lab: after a mission flight,
what actually happened at each point — and the numbers the four constants
must be set from. Without it, "measure the constants from the trace" means
reading thousands of CSV rows by hand, and nobody can repeat the reading.

It READS what every mission flight already writes (find each in the code,
do not assume the paths): the control trace (telemetry/trace.py — the
commanded point target_x/target_y, the estimate stateEstimate.x/.y, drift_m,
the keys held, at 10 Hz), the flight CSV (telemetry/row.py — point_id on
every row taken while holding) and the plan flown (session.py
_keep_plan_flown — the mission exactly as flown). It never needs a drone,
and never changes a file.

  cropwatcher mission-report --flight <flight id>       prints the report
  cropwatcher mission-report --flight <id> --json       the same, as JSON

FOR EACH INSPECTION POINT, IN FLYING ORDER
  leg          the straight 3-D distance flown to it, m
  planned      the planner's time for the leg: the horizontal distance at
               the mission's speed or the height change at CLIMB_RATE_M_S,
               whichever is longer (review.py planned_leg_s), s
  transit      from the commanded point leaving the last spot to reaching
               this one, s
  settle       from the commanded point reaching it to the drone within
               ARRIVE_M and staying there, s
  hold         how long point_id was set, s — and ≥ hold_s or not
  hold drift   while holding: the estimate's distance from the point —
               median, 95th percentile, worst, m
  reached      yes / no (and what the flight did instead)

FOR THE FLIGHT
  flown time against the planner's estimate
  (Mission.estimated_duration_s — the number the battery refusal uses: a
  flight that takes longer than it says is a battery budget that is wrong,
  so the report says so in words, and Samuel must hear of it).

WHAT THE CONSTANTS SHOULD BE, from the flights given (one or several:
--flight may be repeated) — every figure with the flights it came from, so
it can be cited beside the constant:
  ARRIVE_M          above the worst 95th-percentile hold drift, or holding
                    still would never count as arrived
  SETTLE_S          from the settle times measured
  SETTLE_TIMEOUT_S  well above the slowest settle measured
  TRANSIT_MARGIN_S  from the largest (transit − planned) measured
It SUGGESTS. People decide, and write the measurement beside the constant
(CLAUDE.md: never invent a threshold — measure it, and cite it).

Write the calculation as plain functions over rows, not over files, so it
is tested without a disk. A trace with a gap (the radio dropped samples), a
point never reached, a flight that ended early: each is reported in words,
never a crash and never a silent zero.

ITS TESTS (tests/mission/test_review.py):
  [ ] a hand-built trace and CSV for two points: every figure above,
      exactly;
  [ ] gaps, an unreached point, an aborted flight — each reported, none
      crashes;
  [ ] the estimate comparison flags a flight longer than its estimate;
  [ ] `cropwatcher mission-report` on a missing flight says so and exits
      non-zero; --json is valid JSON with the same numbers.
  [ ] Once Hannah's controller is on your branch (step c): a simulated
      mission (PART 1) writes a trace and CSV through the REAL FlightTrace,
      and the report's figures agree with what the simulator did — the
      settle time it reports matches the lag you gave the drone.
