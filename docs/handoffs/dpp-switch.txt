WHAT IT IS
──────────

The operator chooses, per session, whether flights are processed. With it
on, every flight is run through the data pipeline as soon as it lands, and
its verdicts — one per inspection point, or one for a Manual flight — show
on the Control page.


SCOPE — DELIVERED
─────────────────

THE SWITCH
  [x] Per session: on by default in Auto, off by default in Manual; the
      operator's choice wins and lasts until the session ends. Audited
      (processing_set).
  [x] Read as a flight BEGINS and written on its line in meta.json, so a flip
      mid-flight is for the next one.

THE QUEUE (processing.py)
  [x] After the flight's CSV is closed: `cropwatcher process --flight <id>`
      in a CHILD PROCESS, at lower priority — never in the agent's process
      (the 50 Hz flight loop and Python's interpreter lock).
  [x] One flight at a time; 15 minutes at most; exit 0 is success, otherwise
      the command's last line is the reason shown.
  [x] Works installed: the frozen sidecar is the whole CLI, freeze_support()
      first.
  [x] Each flight's state (pending, queued, running, done, failed) in the
      session's meta.json — through the open session's own log, or in the
      file for a closed one.

ON SCREEN
  [x] The switch beside Start session (② Check) and Start mission (③ Fly),
      and in Manual's Data processing panel.
  [x] Results after landing: processing / failed with the reason and
      Process again / not processed with Process this flight / the verdicts
      with readings and frames per point, and an honest placeholder while
      the classify stage is a stub.
  [x] GET /flights/{id}/result, POST /flights/{id}/process — token-gated;
      a flight id that could walk out of the folder is refused.
