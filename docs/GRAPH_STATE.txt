--------------------------------------------------------------------------------
HOW THIS WORKS
--------------------------------------------------------------------------------
Four severities. Only the first one stops work, and it stops work NARROWLY —
naming the area it blocks, never "everything".

  BLOCK   Building here will produce wrong work: a doc contradicts the code on
          something a new feature would build on. Fix, or override explicitly.
  WARN    Trust it less. Read the code rather than the prose for anything
          load-bearing, and re-verify while you are in there.
  DEBT    A known gap that is not dangerous yet. Clear it when convenient.
  WATCH   Will become a problem. No action yet.

The checker's blocking classes are UNMERGED BRANCH, DANGLING, ONE-WAY and STALE.

OVERRIDING A BLOCK is a decision, not an escape hatch: say so in the pre-flight,
name the block and why it does not apply, then add a dated line under OVERRIDES.

CLEARING AN ENTRY requires the fix, not a judgement that it is fine. Re-run
graph_check.py; if the finding is gone, move the entry to RESOLVED with a date.
