SITE PAGES AND VIEWS — editable wording, and visitor vs. operator
=================================================================

WHAT IT IS

Two things that shape the whole website:

1. EVERY WORD ON THE VISITOR SITE IS EDITABLE at /admin/pages — Home, the two
   setup guides and their index, Hardware, Apps, the Projects / Team / Gallery
   headings, and the footer.
   Projects, team members and gallery albums have their own admin sections.
   Home's photos are editable too: the hero image and one per capability card
   are `image` fields, defaulting to stock photos in public/home (CREDITS.txt
   names each one). The strip at the foot of the home page is not a field — it
   is the real gallery, four album covers straight from the table, so it fills
   itself as albums are added.

2. TWO VIEWS. The visitor site (/) and the operator view (/app, /admin).
   Signing in keeps you on the visitor site; only Dashboard switches views.

     Visitor navbar   Sign in (back to the same page) · Dashboard · account menu
     Operator navbar  ← Visitor site · Sign out
     Brand / Home     goes to the home of the view you are in:
                      "/" on the visitor site, "/app" in the operator view

   Dashboard is a protected route. Signed out, clicking it goes to sign-in and
   then straight on to the dashboard (middleware.ts `next`).

   "Dashboard" replaced the working name "analytics deeper dive": it is short,
   and it is what the area is.


ONE WIDTH FOR THE VISITOR SITE

lib/layout.ts SITE_CONTAINER (max-w-6xl, px-6) is used by the navbar, the footer
and every visitor page, so their edges line up all the way down the site. Pages
used to choose their own width — navbar 72rem, home 64rem, Set Up and Hardware
48rem, a project 96rem — and each looked inset by a different amount.

Long-form pages keep a readable line length by holding their TEXT to
PROSE_COLUMN inside the full-width frame, not by narrowing the frame: Set Up
puts the steps in the reading column with the troubleshooting list alongside on
a wide screen, and Hardware lays the parts two to a row.

Dashboard sits with the navigation links rather than out at the far right: it is
another destination on this site, not an action.

TWO PIECES, TWO INDEXES

lib/products.ts is the one list of what a visitor can set up: the desktop app
and the dashboard. Each carries where it runs, what it does, the page key
holding its setup wording, and the installers CI publishes for it.

Both indexes read that list and draw the same card (components/site/ProductCard):

  /setup            a card per piece  ->  /setup/<slug>   its own guide
  /apps             a card per piece  ->  /apps/<slug>    its downloads

/setup/hardware is a real page, not a product slug — a static route beats the
dynamic one, which is why the parts page still works.

The flight agent is deliberately NOT a piece. It ships inside the desktop app,
so nobody who flies the drone sets it up; as a card it read like a second thing
to install. Running it from source is developer work and lives in the repo:
../backend/running-from-source.txt.


A SETUP STEP

Paragraphs, then two optional lists that keep instructions from running
together:

  needs      "What you need" — a checklist, one requirement per line
  commands   "Then run, in order" — one terminal command per line, each a
             button that copies it (components/site/CommandList, copied from
             ../doctor-portfolio's ContactLinks rows)

One command per row, never a chain joined with &&: a row is what gets copied,
and a chain that fails halfway leaves the reader unsure which part ran.
Commands wrap rather than truncate — a command cut off with an ellipsis cannot
be checked before it is pasted.

The desktop guide builds from source in two steps, Mac and PC, because the
commands differ (.venv/bin vs .venv/Scripts, python3 vs python). Windows runs
them in Git Bash: build_sidecar.sh is a bash script, and Git Bash is the shell
the Windows CI runner used to build the published .exe. See
../development/releases.txt — the builds come from CI, not from these pages.


WHEN A SAVE GOES WRONG

Three things, after an operator lost a page of writing on 2026-09-21.

  The error boundary   /admin had none, so a server read that threw was
                       answered by Next's own bare page — "This page couldn't
                       load", a Reload button, an error code — and the editor
                       was replaced mid-edit. app/admin/error.tsx and
                       app/(public)/error.tsx are copies of app/app/error.tsx:
                       what happened, the reference code, and Try again, which
                       re-runs the failed render without a page load.
  The draft            components/admin/useDraft.ts mirrors what is typed into
                       localStorage as it is typed, and clears it only when a
                       save comes back CONFIRMED. On return the editor OFFERS
                       it — "You have unsaved changes… Put them back / Discard
                       them" — rather than restoring silently over the saved
                       version.
  The reason           lib/mutations.ts reason() maps the failure: an expired
                       sign-in, an account without the operator role, a
                       duplicate, an unreachable database. The raw PostgREST
                       message never reaches the browser — it carries policy
                       and column names — it goes to the server log.

Why a save was the moment it broke: every editor calls router.refresh() after a
successful write, which re-runs the server reads. A stale session or a network
blip at that instant becomes a thrown read, and before the boundary that took
the page with it.

PASTING, INCLUDING IMAGES

Pasting a page out of a word processor is how these editors are actually used,
and it was the thing that broke them. An image on the clipboard arrives inline,
as a data: URI, so a pasted Google Docs page saved as several megabytes of
base64 — and a Server Action is capped at 1 MB by default. The save was
rejected before it reached the database, the rejection escaped the editor, and
the error boundary replaced the page.

  In the write-up      components/editor/BlockEditor.tsx uploads every data:
                       image as it appears and points the block at the stored
                       copy, so the document stays small and the picture
                       survives (the clipboard copy would not have).
  Anywhere else        ImagePicker and the gallery's photo area take a click, a
                       dropped file, or a paste. Both are focusable, because a
                       paste event goes to whatever has focus and a div has
                       none by default.
  The limit            next.config.ts raises bodySizeLimit to 4 MB — headroom
                       between a paste and its uploads finishing, not a licence
                       to keep images in prose.
  The guard            lib/save.ts attempt() wraps every save: an action that
                       REJECTS (too large, network gone, deployment restarted)
                       can no longer escape into the error boundary, and a
                       write-up over the limit is refused before the request
                       with an explanation of what to do.

THE EDITOR BAR

components/admin/EditorBar.tsx, extracted from PageEditor, which was the only
editor whose header was sticky. Every editor now wears the same bar: where you
are, the state of the work (unsaved / saving / saved / the failure), and Save —
pinned to the top, so a long form never has to be scrolled back to save it.
Measured: at 1,139 px down the Set Up editor, Save sits at the top of the
viewport.


THE OPERATOR SHELL

/app and /admin share one frame (components/operator/OperatorShell.tsx): a fixed
left sidebar on wide screens, a slim sticky bar on phones. Copied from
../doctor-portfolio's admin studio layout, with the links in two groups —
"Flight data" and "Website" (operators only) — and "View site" above the account
at the foot. The account button shows an initial; its menu holds the email, the
role and Sign out. The old top bar wrapped onto three rows once every link and
the email were in it, which is why the navbar was so tall.

HOW TO MAKE SOMETHING NEW EDITABLE

Add a field to the page's spec in PAGE_SPECS and its current wording to
PAGE_DEFAULTS, then read it on the page with text()/strings()/items()/flag().
The admin form picks it up with no new screen. Field types: text, textarea,
boolean, image, strings (a list of text), items (a list of groups of fields).


DECISIONS

- Defaults live in code; the database stores overrides only. A page with no row
  shows its original wording, so a missing row or a failed read never blanks a
  page, and "Reset to original" is deleting the row.
- Rich inline formatting (bold, links inside a sentence) became plain fields —
  a paragraph list, bullets, a highlighted note, and switches such as "show the
  download buttons". Simpler to edit safely than free HTML, which a public page
  would have to sanitise.
- The admin is wide (up to 110rem) with fields in two columns; long fields and
  lists take the full width. The editor's Save bar stays pinned at the top.


INVARIANTS

- EVERYTHING READ OR SAVED GOES THROUGH normalizeContent. It keeps only the
  fields a page declares, of the declared type, capped in length and count.
  Image fields accept only a site path (/...) or https URL — never javascript:
  or data:. Verified 2026-09-17 against hosted: an operator-stored unknown field
  and a javascript: image both stored, and neither reached the rendered page.
- `next` redirects accept same-site paths only (safeNext). //evil.example and
  absolute URLs fall back to a local page — otherwise a crafted sign-in link is
  an open redirect. Verified: /login?next=//evil.example → /.
- A signed-in user who lands on /login goes to `next` or the visitor home, never
  the dashboard: signing in must not switch views by itself.
- site_pages: anyone reads, operators write (RLS + grants, migration 0009).
