OPERATOR DASHBOARD — the signed-in web app
==========================================

WHAT IT IS

The signed-in area of the web app, /app/*: live telemetry, recorded flights,
zone health, flight comparison, mission planning and settings. It reads what the
desktop app records — it cannot command a drone, because the radio is on the
operator's laptop and not on Vercel.

DECISIONS

- THE DATA PIPELINE ON BOTH PAGES (2026-10-09, Samuel: "the dirty data
  versus the clean data, the grayscale image versus the enhanced image, and
  what we can interpret from it"). From pipeline_results and
  pipeline_findings (migration 20261009000016), in this order:
    What the pipeline found  every finding, worst first: severity in icon and
                             word, the agent's sentence word for word, when,
                             where, the change against expected, the camera
                             note, and each evidence frame original | enhanced
    Data processing          per flight: stage versions, a verdict per point,
                             what the cleaner flagged (sensor values apart from
                             "position not measured"), frames enhanced and
                             unreadable, and per signal a Clean / Raw switch —
                             Clean is what was analysed against what was
                             expected, the findings' stretches shaded AND named
                             under the chart; Raw is every value as recorded,
                             flagged ones as points
    Camera                   Original / Enhanced / Side by side; an enhanced
                             image is always labelled as one
  The session page shows every flight's processing and every flight's raw
  telemetry beside its own 1 Hz vitals — a session is the superset of its
  flights. "Zone health" (the greenhouse predictions table) is gone from both
  pages; the table stays in the database. Not processed, and not migrated,
  are said in words. Checked in a browser against the local stack at 390 and
  1440 px, both themes: no sideways overflow (2026-10-09).
- NOTIFICATIONS ARE KEPT UNTIL READ (2026-10-09, Samuel: "persistent, at
  least in the web app"). Rows in public.notifications, made by the database
  for every operator when a warning-or-worse finding is first inserted
  (migration 20261009000017) — so an operator who was away sees them at the
  next sign-in. ONE provider in the operator shell holds them and ONE
  Realtime subscription delivers new ones at once (announced politely to
  screen readers); the bell in the sidebar and in the phone bar read it. The
  bell says "N unread" in words, opens a panel (the latest, Mark all read,
  View all), and each item opens its finding on the session page and is
  marked read. /app/notifications lists every one, newest first, paged back
  by time, unread marked in a word. A viewer is not notified. A
  notification keeps the words it was sent with. Proved in the browser
  against the local stack: a finding inserted while the page was open
  reached the bell without a reload. The desktop app also raises an OS
  notification when a flight finishes processing with a warning or worse
  (desktop/src/lib/os-notify.ts).
- WHO RAN IT is on every session and flight (operator_name, operator_email,
  stamped by the database — supabase/data-model.txt), shown as name + email,
  "Not recorded" for records from before.
- SESSIONS: EVERYTHING IN A SESSION, NOT JUST ITS FLIGHTS (2026-10-06,
  Samuel). /app/sessions lists every session (who, drone, mode, duration,
  flight count); one session reads like the flight page — summary, sensor
  temperature, height, battery, pressure, where the drone was, camera, zone
  health, raw readings — over the session's OWN vitals (session_samples, one
  a second, Start to End session, flying or not), plus its flights (each to
  its flight page) and its events (audit trail, operators only). A copy of
  the flight page, adapted: raw-readings.tsx takes a column list and
  flight-path.tsx any {x_m, y_m}, the flight page unchanged. The path is drawn
  only from samples with positioned = true. Temperature is the sensor's own:
  room temperature is corrected per flight. Until migration 20261006000013 is
  applied the page says so (getSessionSamples migrated = false), never an
  error and never "nothing recorded".

- One chart component, TimeSeries, with no second-axis seam. Different units are
  different charts. It takes shaded bands (always listed in words beneath) and
  points-only series; its y-axis widens to its longest tick (a fixed 52 px put
  "hPa" on top of "1026.55"). It always ships a table view, because light-mode --series-3
  and --series-4 measure under 3:1 (2.74 and 2.11).
- Compare keeps each flight's colour in the URL (?f=<id>:<slot>), so removing one
  flight never repaints the others. Four flights maximum — the four validated
  series colours.
- Settings is read-only. The geofence the drone obeys is the agent's --fence
  flag; a value stored in a browser would change nothing while looking as though
  it had. Each value says where it really lives.
- Headings use --heading, a token separate from --primary, because a heading is
  text and has to clear 4.5:1 on every surface. Measured: 6.63/6.07/6.46 light,
  5.33/4.82/5.83 dark (surface / surface-2 / background).
- All Supabase access goes through lib/queries.ts (reads) and lib/mutations.ts
  (writes). Never createClient() inside a component.


INVARIANTS

- Reads throw; they never return `data ?? []`. An empty fallback rendered a
  database error as "No flights recorded yet". QueryError logs the Postgres
  message server-side and error.tsx offers a retry.
- Set the Realtime token before subscribing. The SSR browser client loads its
  session lazily, so a channel joined first subscribes as anon, RLS delivers
  nothing, and the channel still reports SUBSCRIBED. Measured: 0 rows in 5 s from
  the page versus 16/16 from a client that called realtime.setAuth().
- Backfill after subscribing. Rows written between the server read and the socket
  opening arrive on neither; useLiveTelemetry fetches everything after the last
  index it holds once subscribed.
- Format times in the browser (<LocalTime>). toLocaleString() in a Server
  Component uses the server's zone — UTC on Vercel — so 4:45 PM Eastern rendered
  as 8:45 PM with no label.
- Y-axes fit the data with computed ticks. Recharts' zero baseline flattened
  3.7–4.1 V into a line, its own ticks inside a domain were uneven, and a domain
  *function* drew no axis at all for some ranges.
- Chart text uses --muted, never --axis. --axis measures 2.86:1 light and 2.94:1
  dark: it is for lines only. Legend text is forced to --foreground, because
  Recharts colours it with the series by default.
- Height is ground-relative or it is not shown as height. Without ground_z_m the
  raw Lighthouse z is labelled as such, and Compare leaves that flight out —
  floor level varied 0.85–1.40 m between runs. The agent already stores
  ground-relative z, so never subtract it again here.
- The nav marks the LONGEST matching route active. A prefix test marked /app
  active on every page.
- ZONE HEALTH COLOURS ASSUME health_score IS 0–1. Nothing enforces that yet,
  because nothing writes the column: the model that will (see ROADMAP phase 11)
  is not wired up. Pin the range when it lands, or a score on a 0–100 scale
  will paint every zone at the top of the sequential ramp and look like a
  uniformly healthy greenhouse.
