CAMERA — built end to end; the deck delivers whole frames
=========================================================

WHAT IT IS

The Control page's Camera tab, and everything behind it: a frame source in the
agent, a route that serves frames, the window's content policy, and the tab that
renders them. Three sources: none, a generated test pattern, and the AI deck's
own Wi-Fi image streamer.

THE DECK DELIVERS WHOLE FRAMES. This page said until 2026-10-09 that no whole
real frame had ever arrived (the first capture, 2026-09-23, stalled a third of
the way in). That had DRIFTED: the lab laptop holds 8 748 recorded frames —
324×244, 8-bit grayscale, real images of the lab — from 43 sessions between
2026-09-24 and 2026-10-09 (836 on 09-24, 3 800 on 09-30, 3 167 on 10-05).
They are dark (median brightness 61 of 255), which is why the data pipeline
enhances them (../pipeline/enhance.txt). Verified by reading the frames
themselves, not the logs.

THIS IS NOT VIDEO. The window pulls one still every 200 ms — about 5 fps at
best — and the deck has delivered 0.7–4.9 (camera-firmware.txt).

THE RADIO CANNOT CARRY FRAMES — the 50 Hz setpoint stream shares it — so the
deck has its own Wi-Fi; deck presence is read as a param (deck.bcAI). Why,
measured: camera-firmware.txt, "THE RADIO".


THE SOURCES — chosen by DRONEDECK_CAMERA

  (unset)  NoCamera     the default. Frames are None; the route answers 204
  test     TestPattern  a generated 320x320 PNG
  deck     DeckStream   the deck at DRONEDECK_DECK_ADDR (192.168.4.1:5000)

THE DESKTOP APP SETS `deck` for its bundled agent (lib.rs, spawn_agent), so
`pnpm app` is the whole test: build, launch, join the deck's Wi-Fi, open the
Camera tab. An app opened from Finder never sees a terminal's variables, so
leaving it to the environment meant the app's agent always had no camera.

THE DECK CAN JOIN THE OPERATOR'S NETWORK INSTEAD — drone-wifi.txt. Then no
switch is needed: the agent reads the deck's new address off the drone's console
and DeckStream.set_host moves the stream there. The access point is what the
deck falls back to when no network has been set.

For a bare `dronedeck serve`, `deck` stays opt-in because it needs the laptop JOINED to the deck's access point
("WiFi streaming example"), and while it is, the laptop has no internet — the
agent cannot sync, and a remote assistant driving the laptop loses its link.
A second network adapter (USB Wi-Fi or ethernet for the internet) removes that.


WHAT RUNS ON THE DECK, ITS WIRE FORMAT, WHY THE FEED IS SLOW AND STALLS, and
the firmware being built to fix it: camera-firmware.txt.

Raw frames are re-encoded to greyscale PNG; JPEG (format 1) passes through. A
colour sensor would show its Bayer pattern as fine texture — demosaicing is not
done. One background thread owns the socket and keeps only the latest frame;
it reconnects forever with backoff, and a frame older than 2 s is not served.

The test pattern MOVES: a band sweeps down and a
counter bar advances, because a still image cannot tell a live feed from a frozen
one — which is the exact failure a real feed has.

The PNG encoder is written by hand with zlib from the standard library. Pillow
would be clearer and is tens of megabytes into a binary that ships to operators
inside a 48 MB installer, for a picture nobody sees once a real camera exists.


THE ROUTES

  GET /camera         status as JSON: live, kind, reason, deck_fitted
  GET /camera/frame   the latest frame, or 204 when there is none

BOTH ARE UNAUTHENTICATED, deliberately. An <img> cannot send a header, so
requiring the control token would mean putting it in a query string — which the
WebSocket deliberately avoids because a query string lands in access logs. These
routes are read-only, they command nothing, the agent binds localhost, and
/status is already open and carries more.

204 rather than 404 for "no camera": an empty body the window can tell apart
from a broken route.


DECISIONS

- The deck source was built against the captured header and a stand-in deck
  (same format, on localhost) rather than waiting for a whole real frame: the
  parser, the reconnect and the staleness rule are knowns; the deck is not.
- Built against a test pattern rather than waiting for the deck. The deck is one
  unknown; the route, the content policy, the four states and the cache
  behaviour are four knowns, and proving them now means the lab session is
  plug-in-and-check instead of build-and-debug.
- `deck_fitted` has three states and they need different things done about them:
  fitted with no link is a lab problem, not fitted is a hardware one, and null
  means no session has run the checks yet.
- THE FEED IS THE WINDOW'S, NOT THE TAB'S (2026-10-24, changed). The tab used
  to stop pulling frames when hidden, and to start from nothing when shown —
  so leaving it and coming back looked like the camera switching off (Samuel:
  "the camera feed should always be on"). lib/cameraFeed.ts now runs for as
  long as the window is open: a frame every 200 ms while any camera view is
  on screen, every 2 s while none is, and the agent's camera status every 2 s
  always. Returning finds a current picture.
- One dropped frame is a hiccup; five in a row is a stopped feed. Reporting the
  first would make a normal feed look broken.
- A stopped feed is retried, not reported and abandoned. The agent reconnects
  to the deck on its own; the tab re-asks it every 2 s while there is no feed,
  so rejoining the deck's Wi-Fi or a deck that recovers needs no click. Before
  this, the first real image vanished for good after one stall.

HOW THE LINKS FIT (the question an operator asks first)

  Crazyradio dongle  2.4 GHz, NOT Wi-Fi — flight control and telemetry only
  deck's Wi-Fi       raised by the AI deck's ESP32 whenever the drone is on;
                     carries the camera and nothing else
  this laptop        must JOIN the deck's Wi-Fi to see frames — and while
                     joined it has no internet (no Supabase sync)

Switching the laptop's Wi-Fi from a button was considered and not built:
joining the deck with `networksetup` works, but rejoining a campus network the
same way failed (-3900) and only toggling Wi-Fi power recovered it; and the
switch takes the laptop offline. The lasting fix is the deck JOINING an
existing network ("Connect to an access point" in the firmware's Kconfig) or
wired internet on the laptop, so both links are up at once.


RECORDING (2026-09-24) — a session's frames, to disk first

  <session folder>/frames/000001.png    every frame, as received
  <session folder>/frames.csv           seq, recorded_at, t_s, file, width,
                                        height, bytes, x_m, y_m, z_m, upload

Every frame of a session is kept on the laptop — unless auto-capture is off
(capture.txt). The CAPTURED ones are marked upload=1 and go to the private
flight-frames bucket through the outbox (offline-sync.txt): since 2026-10-24
the frames that differ from the last captured one, at most two a second
(capture.txt, the rule); before, simply two a second. Position is the drone's estimate as the frame arrived;
empty — not zero — when there is none. Standby records nothing.

IN A SESSION THE TAB SHOWS THE RECORDING — while auto-capture is on: the
newest frame read back FROM DISK, and a backlog scrubber (◀, a slider, ▶, "n/N · m:ss", Live) to walk
back through the session. What is watched is what was saved and what uploads.
Outside a session, or with auto-capture off (the recording then grows only
on a manual capture, and following it would freeze the picture), the tab
shows the live feed as it comes, even when uneven.

HOW FAST, MEASURED (2026-10-24, camera/rate.py). Under the picture, one line
from both ends of the link: what ARRIVES (frames a second over the last 10 s,
their size, raw or jpeg, the longest gap — the open one included) and what
the GAP8 SAYS each frame cost it (capture, encode, send, read off the drone's
console; its sum bounds what the deck can produce). Send dominating means the
ESP32 / Wi-Fi is the slow part; the deck's ceiling far above the arriving
rate means frames are held between the ESP32 and this laptop. In /camera as
`rate` and `deck_timing`.

A STALL IS SAID, NEVER SILENT: the last frame stays up, dimmed, with
"Camera stalled · no new frame for N s" (or "Reconnecting" while the agent is
working towards a picture).

Verified: real upload as the operator to flight-frames (2 of 6 frames chosen
at 10 fps, i.e. two a second, plus frames.csv), outbox emptied, test objects
deleted. NOT yet: a real session on the drone.


INVARIANTS

- A RECORDED FRAME IS NEW ONLY WHEN ITS NUMBER RISES. "latest" keeps answering
  with the last frame after the deck stalls; counting that as fresh would show
  a frozen picture as live.
- CONNECTING IS NOT "NO SIGNAL". While the drone joins or rejoins Wi-Fi, or the
  camera is reconnecting to a joined deck, the tab shows a spinner and the
  reason. A new address from the deck kicks the camera to retry at once
  instead of waiting out its backoff.

- THE LAST GOOD FRAME STAYS UP THROUGH A DROP-OUT, for 30 s, with "Reconnecting ·
  last frame N s ago" over it. Frames are fetched as blobs, one at a time, so a
  failed request never replaces the picture (an <img> pointed at a URL that
  204s shows nothing). The tab stops pulling after 10 s of misses and goes back
  to asking the agent. Reported 2026-09-24: moving the drone quickly "cut" the
  feed — the tab had been dropping to NO SIGNAL after 5 missed frames (1 s).
- A READ SILENT FOR 2 S IS A STALL (was 5 s); the agent reconnects at once and
  doubles from 0.2 s. A healthy raw frame takes ~32 ms (the GAP8's count).
  THREE CONNECTIONS IN A ROW WITH NOT ONE BYTE (2026-10-24) slow the retries
  to every 5 s and make the Camera tab say which chip is silent, from the
  drone's own console (camera-firmware.txt, "WHICH CHIP IS SILENT").
- img-src includes blob:, for the above.

- Frame size comes from each frame's header, never a constant. The only
  constant this code had — 320x320 — was a guess; the deck measured 324x244.
  The tab letterboxes (object-contain) rather than cropping to its square box.
- A stale frame is not live. A frozen last frame looks exactly like a working
  feed, so DeckStream stops serving it after 2 s and says why.
- The frame URL carries a changing stamp and the route sends `no-store`. Without
  both, the <img> shows the first frame forever and the feed looks frozen when
  it is fine.
- img-src must list the agent's origin in tauri.conf.json. `default-src 'self'`
  covers images when img-src is absent, so the window silently renders nothing —
  no error, no broken-image icon in some cases, just an empty frame.
- Deck presence is a PARAM, not a log variable. It cannot ride the 10 Hz
  telemetry stream, and asking for it there would be looking in the wrong place.
