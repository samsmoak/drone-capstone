SET UP — a drone out of the box to a session, in five steps
============================================================

WHAT IT IS

The Set up page (sidebar). One list, one step open at a time:

  1. Connect the drone          Crazyradio in, drone on (ticks itself)
  2. Install drone software     check → install what is missing → unplug → verified
  3. Measure the base station   record the start → 1.00 m forward → record
  4. Connect the camera to Wi-Fi   → the Drone Wi-Fi page (drone-wifi.txt)
  5. Start a session            → Home

Step 2 puts on a new drone exactly what the first drone was given by hand.
Step 3 tells the drone where the base station stands, so it can turn the
station's beams into a position — without it Auto refuses every mission.

DECISIONS

- WHAT A DRONE HAS IS READ, NOT ASSUMED. cwsetup.fw (present only in our
  firmware) says whether main is ours and which version; cwsetup.deck, stored
  PERSISTENTLY on the drone after a verified install, says which deck bundle it
  carries — the deck's own chips cannot report their firmware over the radio.
  Only what is missing or older is flashed; a set-up drone is told so.
- The deck's two parts install together: they were tested together, and the
  marker records them as one bundle.
- The agent does the flashing: it is the radio's only owner (standby paused,
  resumed after). Refused during a session.
- Words on the page are instructions; the why is here.
- STEP 3 IS `cropwatcher geometry`'s ONE-STATION WALK, NOT A SECOND ONE
  (2026-10-05, Samuel: "everything has to run in the software").
  StationMeasurement hands the two button-press records to estimate_single()
  as the samples it would have collected, so the app and the terminal solve,
  refuse and explain identically (flight-safety.txt, WHEN THERE IS ONLY ONE
  STATION). Motors off, over whichever link is open — standby or a session —
  and refused while flying. A refusal forgets the start record: the start
  mark is the one place the operator knows the drone still is.
- STEP 3 IS DONE WHEN THE DRONE SAYS SO: /station reads the drone's own
  bsReceive / bsGeoVal / Kalman variance (assess_positioning, the checks'
  rule), polled each second. Done = positioning ready, not "a record was
  taken". "Measure again" reopens it — after a station is moved, the stored
  place is wrong and nothing on the drone can tell.
- STEP 2 HOLDS THE LIST ONLY WHILE IT HAS WORK (2026-10-05). Its state is
  the agent's and starts "idle" every launch, so "done" required pressing
  Check the drone again each run — and that hid step 3 from an operator whose
  drone was fully installed: the station was never measured and ② Check
  showed the drone "92 m from the start". Step 2 now leads only while
  checking, installing, unplugging, failed, or with parts to install; its
  "Check" button opens it any time. Every step reopens by its button.
- AFTER A SUCCESSFUL STORE THE ESTIMATOR IS RESET (preflight.reset_estimator)
  with the drone still on the floor: it ran on no geometry until then, metres
  off, and a filter that far out can reject the beams that would correct it.
  The step then reads done only when the drone says positioning is ready.
- NOTHING RESTARTS THE DRONE BETWEEN THE TWO RECORDS: the camera watchdog
  (api/rest.py Agent.rejoin) waits while Session.measuring_station — a
  restart drops the link and resets the heading the second record is checked
  against.
- IT COMES BEFORE THE CAMERA'S WI-FI: flying needs a position, the camera is
  diagnostic only (CLAUDE.md, Out of scope).
- ONE STATION: only the first station seen in both records is measured. With
  two received, the second stays unmeasured and is not used; the two-station
  walk (ten records, by hand in the air) stays in the terminal for now.


INVARIANTS

- ORDER: main, then lighthouse (main names the image the deck needs, so the
  deck is asked AGAIN after main), then camera (the GAP8 is written THROUGH
  the ESP32), then wifi.
- A POSITIONING DECK WITHOUT ITS IMAGE IS DEAF (2026-10-01, the second lab
  drone cf-002d00263234511236373639): detected (deck.bcLighthouse4 = 1) but
  sitting in its bootloader — lighthouse.status 0, nothing received, the
  position running away — while both base stations were fine. The drone says
  so itself (deck memory: fw_upgrade_required), so it is read, never assumed,
  and needs no marker. The first write did NOT survive a battery unplug that
  day, so the unplug Set up already asks for doubles as the check that it
  stays; a deck that loses it is reported, not marked done.
- The deck is flashed with cflib's own deck path (flash_firmware.py
  flash_lighthouse_deck): only the deck is in the target list, so the STM32
  and the nRF51 are skipped; cflib leaves the drone in its bootloader, so it
  is restarted into its firmware after.
- AFTER THE ESP32 IS FLASHED THE GAP8 DOES NOT START until the battery is
  unplugged ~10 s (Bitcraze Discussion #1305; measured 2026-09-24 — a restart
  over the radio is not enough). The page asks, and the check counts only once
  the drone has left the radio AND come back: the drone's console keeps old
  lines, and "GAP8 running" from before the flash must not pass for after it.
- NOT BELOW 3.8 V: a flash that loses power can leave a drone unable to start.
- The marker is written only after the camera is seen starting.
- AN UNMOVED DRONE IS NAMED, NOT CALLED A DISAGREEMENT (NOT_MOVED_M 0.10 m,
  2026-10-05): two records whose station positions match are the same place.
  That day's terminal run read "disagree by 100 cm … 2.45 m away from both" —
  an unmoved drone — and a still drone's 50-sweep averages agree to 1e-5 rad.
  The guard also exposed a test (test_geometry.py, the mirror test) that had
  been feeding one sample twice since it was written.
- The page cannot tell a Crazyflie 2.1 from a 2.1 Brushless (the radio does not
  say; cflib's bootloader reports both as "cf2"). It is for the 2.1 + AI deck.
