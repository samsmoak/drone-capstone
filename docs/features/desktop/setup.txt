SET UP — a drone out of the box, ready to fly, in five steps
============================================================

WHAT IT IS

The Set up page (sidebar). One list, one step open at a time:

  1. Connect the drone          Crazyradio in, drone on (ticks itself); when it
                                cannot reach the drone: the agent's reason and
                                the three fixes, in the order they work
  2. Install drone software     COMMANDS ONLY — copy a line, quit DroneDeck,
                                run it in Terminal: install what is missing,
                                reinstall one part, or read only (--check)
  3. Base stations: one channel each   each station on USB → channel 1 / 2
  4. Connect the camera to Wi-Fi   → the Drone Wi-Fi page (drone-wifi.txt)
  5. Fly                        → Control › Auto (auto-control.txt)

Step 2 puts on a new drone exactly what the first drone was given by hand —
and on a new AI deck too: a replaced deck is told apart by its factory serial
and gets its camera and Wi-Fi software without being asked. Any installed
part can be written again with its own line ("Install or reinstall" reopens
the step).
Step 3 puts every base station on its own channel, so the drone can decode
their sweeps. Telling the drone where the station stands is part of flying,
not set-up: Control › Auto › ② Position (auto-control.txt) — it was step 4
here until 2026-10-05, where the operator could not find it.

DECISIONS

- THE INSTALL IS A TERMINAL COMMAND, NOT A BUTTON (2026-10-24, Samuel: "put
  it in a command — which the user can run and get the firmware on the
  drone"). Step 2 checks and lists the parts, then shows the command with a
  Copy button; the ticks add `--reinstall <parts>`:

      cropwatcher setup                          check, then install what is needed
      cropwatcher setup --check                  check only; change nothing
      cropwatcher setup --reinstall camera,wifi  write those parts again too

  It is the same engine (DroneSetup) — same order, battery floor, unplug,
  verification and marker — printing each step and a boxed UNPLUG prompt.
  Exit 0 done, 1 failed, 2 DroneDeck open.
  THE APP IS QUIT FIRST: the radio has one owner, and DroneDeck's agent holds
  it while the app is open, so a second program would read "no drone". The
  command asks 127.0.0.1:8765/health and refuses while it answers, rather
  than reporting a missing drone. It does not borrow the app's agent token to
  ask it to let go: that token is the app's alone.
  WHICH COMMAND: an installed app has no Python on PATH — its own agent
  binary is the whole CLI (packaging/sidecar.py), so the line is
  `…/DroneDeck.app/Contents/MacOS/cropwatcher-agent setup` (PowerShell form
  `& "…" setup` on Windows; a developer's venv `cropwatcher setup`). The agent
  computes it (setup_cli.command_line), never the page, so it is the real path.
- WHAT A DRONE HAS IS READ, NOT ASSUMED. cwsetup.fw (present only in our
  firmware) says whether main is ours and which version; cwsetup.deck, stored
  PERSISTENTLY on the drone after a verified install, says which deck bundle it
  carries — the deck's own chips cannot report their firmware over the radio.
  Only what is missing or older is flashed; a set-up drone is told so.
- The deck's two parts install together: they were tested together, and the
  marker records them as one bundle. A tick on either reinstalls both.
- A REPLACED AI DECK IS TOLD APART BY ITS FACTORY SERIAL (2026-10-15). The
  marker lives on the drone, so before this a new deck on a set-up drone read
  "installed" and got nothing. Every deck carries a 1-wire memory with a
  unique serial, which cflib reads before the link opens (OWElement.addr; the
  AI deck is vid 0xBC pid 0x12, crazyflie-firmware aideck.c). Its CRC-32
  (never 0) is saved as cwsetup.deckid beside cwsetup.deck after a verified
  install; a different serial lists camera and Wi-Fi as to install, and the
  page says why. The serial saved is the one read AFTER the unplug — the deck
  that actually started the camera. Kept on the drone, not the laptop, so a
  second laptop reads the same record.
  Rejected: keeping it on the laptop (no firmware change, but a second laptop
  would not know). Uncaught by design: the same deck reflashed elsewhere keeps
  its serial — that is what Reinstall is for.
- A SERIAL THAT CANNOT BE READ leaves cwsetup.deck alone to decide, and is
  saved as 0. Reinstalling on every check instead would loop: nothing could
  ever record that it was done.
- NO BUTTON WRITES TO THE DRONE (2026-10-24, Samuel: "i dont want people
  accidentally pressing a button to reinstall a firmware"). Step 2 is lines
  to copy: install what is missing; reinstall ONE part — drone firmware
  (--reinstall main), positioning deck (lighthouse), camera and camera Wi-Fi
  (camera,wifi: one bundle); and read only (--check). Its one button, Read
  what is installed, changes nothing. The reinstall ticks that built the line
  (2026-10-15) are gone with the Install button: a part per line, not one
  line for everything — rewriting the drone firmware to fix a camera adds
  minutes and risk. Reinstalling still refuses a low battery, keeps the
  order, and a deck that is not fitted is not written.
- The agent's engine does the flashing, run ONLY by the command in its own
  process with the app quit (above). POST /setup/install was removed
  (2026-10-24) so nothing in the app — or anything holding its token — can
  flash the drone; test_api.py TestSetupWritesNothing pins it.
- STEP 2 IS ALWAYS OPEN, WITH NOTHING IN ITS HEADER (2026-10-24, Samuel, again:
  "remove that install button"). The header's "Install or reinstall" only
  opened the step, but it read as an install button and the commands hid
  behind it. The step is open on every visit, never takes the list's place
  (the list goes connect → channels → Wi-Fi), and its one button is "Check
  what's on the drone" — "only reads, it never writes". The commands are
  fetched until they arrive (every 3 s): an agent still starting no longer
  leaves them behind a Try again.
- Words on the page are instructions; the why is here.
- STEP 3 SETS CHANNELS THE WAY BITCRAZE'S CLIENT DOES (cfclient
  basestation_mode_dialog.py, "Set BS channel"): a Base Station 2.0 on USB is
  a serial console (vid 0x28de pid 0x2500); "mode" reads "Current mode: N",
  "mode N" + "param save" sets and keeps it; the reply is read back and a
  channel the station does not confirm is a failure in words. WHY: Bitcraze,
  "Every V2 base station in the system must be set to a unique channel";
  channel 0 is "not supported" — overlapping sweeps are not decoded while the
  station's data still is. The step reads done once the drone decodes
  sweeps (bsReceive). Measured 2026-10-05: one spot, no sweep in 8 s and
  bsReceive 10 % of samples; later, station 0 decoded on every reading.
- EVERY STAGE FROM THE DECK TO A POSITION IS SHOWN (step 3, ② Position, and
  Manual's map): the positioning deck detected (deck.bcLighthouse4) → its
  firmware running (the deck memory's is_fw_upgrade_required, read once per
  link, never in flight — 2026-10-24) → light on the
  sensors (lighthouse.width0-3) → the station's data read (bsCalVal) →
  sweeps decoded into angles (bsReceive) → its place stored (bsGeoVal) → in
  use by the drone (bsActive: calibration, place and sweeps together) →
  settled (Kalman spread < 5 cm). The first row that is not ✓ is the one to
  fix — and the agent says which, with its fix, above the rows
  (flight/position_stages.py first_blocker, /station `blocker`), so the map,
  the stages and ② Position never disagree. A deck not detected, or not
  running its firmware, reads exactly like stations that are off (0 of 4),
  which is why it comes first. The telemetry stream carries them (stream.py, six log blocks; the
  firmware allows 16).
- bsReceive IS THE DECODE SIGNAL, validAngles IS NOT. The firmware sets a
  station's bsReceive bit only when a sweep yields angles
  (crazyflie-firmware lighthouse_core.c: processFrame →
  pulseProcessorProcessPulse true → usePulseResult). validAngles read 0
  while bsReceive showed station 0 decoding on every reading (2026-10-05).
  This doc and the app said "validAngles 0 = not decoding" for one build
  that night; that was wrong, and is corrected here and in the code.
- NO LIGHT IS NOT "NO SIGNAL" (2026-10-24: a whole session read 0 of 4
  sensors while both stations were measured). flight_guard problems() says
  "No light reaches the positioning deck — all 4 of its sensors read 0"
  (stations' LEDs, line of sight, then the deck) apart from "light, but no
  sweep decoded" (give each station its own channel). The session-start
  reason and the right strip's Base stations vital ("0 of 2 — no light on the
  deck" / "— light, not decoded") say the same.
- ONE CAUSE, SAID ONCE (flight_guard problems): received but not measured
  says "measure the base station" only — not also "wait for the
  calibration" (already read) or "may be blocked or off" (it was received).
  ② Check shows the agent's own reason and a Check again button
  (Session.retry, allowed while READY), so a station measured mid-session
  is picked up without ending it.
- STEP 2 HOLDS THE LIST ONLY WHILE IT HAS WORK (2026-10-05). Its state is
  the agent's and starts "idle" every launch, so "done" required pressing
  Check the drone again each run — and that hid the measuring step from an operator whose
  drone was fully installed: the station was never measured and ② Check
  showed the drone "92 m from the start". Step 2 now leads only while
  checking, installing, unplugging, failed, or with parts to install; its
  "Check" button opens it any time. Every step reopens by its button.
- AN UNMOVED DRONE IS NAMED, NOT CALLED A DISAGREEMENT in the terminal's
  two-record walk (`cropwatcher geometry`; NOT_MOVED_M 0.10 m, 2026-10-05): two records whose station positions match are the same place.
  That day's terminal run read "disagree by 100 cm … 2.45 m away from both" —
  an unmoved drone — and a still drone's 50-sweep averages agree to 1e-5 rad.
  The guard also exposed a test (test_geometry.py, the mirror test) that had
  been feeding one sample twice since it was written.
- The page cannot tell a Crazyflie 2.1 from a 2.1 Brushless (the radio does not
  say; cflib's bootloader reports both as "cf2"). It is for the 2.1 + AI deck.
