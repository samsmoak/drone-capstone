--------------------------------------------------------------------------------
1. WHAT IT IS
--------------------------------------------------------------------------------
The AI deck has two chips: the GAP8 reads the camera and sends each frame to
the ESP32, which sends it over Wi-Fi to this laptop. Both run Bitcraze
firmware, built here with small patches. This page is what they do, how the
frames look on the wire, and why the feed is as slow as it is.

3. THE WIRE FORMAT, measured 2026-09-23 from the real deck
--------------------------------------------------------------------------------
  every packet   <HBB     length (counts the 2 routing bytes), routing 0x63 0x05
  image header   <BHHBBI  magic 0xBC, width, height, depth, format, size
  data           packets of 1020 payload bytes until `size` bytes arrive
  measured       324 x 244, depth 1, format 0 (raw), size 79056 = 324*244

Format 1 is JPEG and the agent passes it through untouched; raw is re-encoded
to a greyscale PNG. Every reader downstream decodes either (cv2).

--------------------------------------------------------------------------------
4. WHY IT IS SLOW — what is known
--------------------------------------------------------------------------------
Measured: 0.7–4.9 frames a second across the lab's sessions; 3.7 a second
even at −59 dBm. The GAP8 itself reported capture=76 ms and transfer=32 ms
for a healthy frame — about 9 a second if nothing downstream held it. So the
time is lost between the GAP8 and this laptop, and two causes were found in
the ESP32's code (2026-10-24):
  - MODEM SLEEP. A station defaults to WIFI_PS_MIN_MODEM and nothing in
    Bitcraze's code turns it off: the radio sleeps between beacons, and the
    laptop's ACKs wait for it to wake.
  - NAGLE. Each 1 020-byte CPX packet is its own send(); a frame's last
    partial segment waits for the laptop's delayed ACK.
And a third, structural: a raw frame is 79 KB, so any slowness is paid 79
times over. JPEG frames fit 30 KB at most.
The GAP8 waits for each send before the next capture (no pipelining), so a
slow send also lowers the capture rate. Not changed yet.

THE STALL IS ON THE DECK. Read over the radio (2026-09-24): "GAP8:
capture=76ms ... transfer=1150948 ms" and "ESP32: Error occurred during
sending: errno 113". The GAP8 sat in one frame's send for 19 minutes; a
healthy frame took 32 ms. A weak signal (the deck's chip antenna, −84 dBm at
the edge) is the likeliest trigger. JPEG shortens each send; it does not fix
the stall.

--------------------------------------------------------------------------------
5. DECISIONS
--------------------------------------------------------------------------------
• MEASURE, THEN CHANGE (2026-10-24, Samuel agreed). Cheapest first: the
  ESP32's two settings (no image change at all), then JPEG. Fewer pixels was
  offered and declined — "I don't want to … reduce … the pixels".
• JPEG IS A COMPILE-TIME CHOICE in Bitcraze's streamer (streamerMode), so it
  is a patch and a build, not a setting. Its buffer is raised from 15 KB to
  30 KB: the encoder stops when the buffer runs low (jpeg_encoder.c), so a
  busy scene that needs more is CUT SHORT at the bottom, not overrun.
• THE GAP8 IS BUILT IN DOCKER, AND ONLY IT. The GAP SDK is Linux-only and
  Bitcraze build their release in bitcraze/aideck (release.yml). CLAUDE.md
  #7 keeps the agent and the app out of containers; this makes one file,
  flashed over the radio by the agent's own flasher. The owner did not object
  when asked (2026-10-24); the ESP32 still builds natively.
• --stock builds the same source unpatched, to check the build against
  Bitcraze's release: same size, 467 of 61 472 bytes differ (build paths and
  stamps).
• THE BUNDLE IS RAISED ONLY AFTER THE LAB. Raising it is how Set up offers
  the update (a drone whose cwsetup.deck is lower reads "needed"); doing it
  before the pair is measured faster would push unproven firmware onto every
  drone.

--------------------------------------------------------------------------------
6. THE ESP32's OTHER PATCH (flashed 2026-09-24)
--------------------------------------------------------------------------------
Stock firmware (2025.02 included) can close one client twice; the stale
"disconnected" bit then drops EVERY later client in the same millisecond.
close-client-once.patch closes each once and clears stale bits before accept:
0 of 11 clients dropped instantly after (all, before); 55 frames / 15 s at
−59 dBm. Flashing the ESP32 leaves the GAP8 NOT STARTING until the battery is
unplugged ~10 s (Bitcraze Discussion #1305). The GAP8 BOOTLOADER needs a JTAG
programmer — do not plan on it.

8. THE RADIO — moved here from camera.txt (2026-10-24)
--------------------------------------------------------------------------------
MEASURED 2026-09-23, IN THE LAB, ON cf-002f002a3334471239333335

  before reseating   every deck param 0 · 1-Wire memories enumerated: 0
  after reseating    deck.bcAI YES    · 1-Wire memories enumerated: 1

Deck detection reads an EEPROM on each deck over a SINGLE shared pin, at boot.
Zero memories with the boards visibly attached was one contact fault, not
several missing decks — reseating fixed it and the AI deck is now detected.

deck.bcLighthouse4 IS STILL 0, and only one memory enumerates. Whatever was
wrong for the AI deck is still wrong for that one, and it costs every flight
its position (flight-safety.txt). Worth the same treatment.

CPX OVER THE RADIO DOES NOT WORK, and the reason is cflib, not the firmware.
cflib ships `cflib.cpx.transports.CRTPTransport`, which is why it first looked
viable — but READ IT: every method is `pass` and its own comment says "This
connection will not really work...". The only real transports are
SocketTransport (TCP, i.e. the deck's Wi-Fi) and UARTTransport. So the deck's
Wi-Fi IS required after all, and an earlier note here saying otherwise was
wrong.


WHAT THE RADIO CAN AND CANNOT DO

  ask whether the deck is fitted      YES — deck.bcAI, a param read
  carry the frames                    NO

`deck.bcAI` is read during the checks, beside `deck.bcLighthouse4`, and lands on
the session snapshot as `ai_deck`. It gates nothing; it is recorded and shown.
None rather than False when it cannot be read: firmware that does not publish
the param has not said "no deck", and recording a guess as a measurement is what
CLAUDE.md #5 exists to stop.

The frames cannot come the same way. Usable CRTP throughput is a few KB/s and a
single 320x320 frame is tens of KB — but the real objection is not bandwidth, it
is that THE SAME LINK CARRIES THE 50 Hz SETPOINT STREAM. The Crazyflie stops
accepting control below about 10 Hz of commands and drops; congesting the radio
with image data risks the drone. That is why the deck carries its own Wi-Fi chip,
and it is why this is a lab problem rather than a coding one.

Bitcraze's CPX can route deck data over CRTP, so a still frame every few seconds
is possible in principle. It still shares the link with control, it needs the
deck flashed for it, and it is not video.
