DESKTOP APP — the Tauri shell and the bundled agent
===================================================

WHAT IT IS

A Tauri v2 window (React + Tailwind) that bundles the flight agent as a sidecar
binary, so an operator installs one thing and never sees Python. It is not a
second copy of the web app: this is the only surface that can command a drone,
because it runs on the machine holding the radio.

THE FOLDER IS `desktop/`.

  desktop/src/          the React UI (see pages-and-windows.txt)
  desktop/src-tauri/    the Rust shell
  desktop/src-tauri/target/release/bundle/macos/CropWatcher.app   the built app


WHERE IT LIVES

  desktop/src-tauri/src/lib.rs            spawns the agent, holds the token,
                                          explains why the agent stopped
  desktop/src/lib/agent.ts                typed REST + WebSocket client
  desktop/src/main.tsx                    close = end the session tidily
  desktop/scripts/sidecar.mjs             `pnpm sidecar`: finds the venv Python
  desktop/scripts/open-app.mjs            `pnpm app`'s "open it", on any OS
  backend/agent/packaging/                PyInstaller spec, build_sidecar.py,
                                          verify_sidecar.py
  scripts/install.mjs                     THE install: setup, build, install
  scripts/setup.mjs                       toolchain checks + dependencies
  scripts/lib/radio-access.mjs            the radio's one-time admin step per OS
  .github/workflows/desktop-install.yml   runs install.mjs on arm Mac, Intel
                                          Mac and Windows; uploads nothing

Install (any OS):  node scripts/install.mjs        (--open, --no-install, --dev)
Set up only:       node scripts/setup.mjs          (--check, --dev)
Build:  cd desktop && pnpm tauri build      <- builds BOTH halves

`pnpm tauri build` re-freezes the agent first, because tauri.conf.json's
beforeBuildCommand is `pnpm build:all` (sidecar, then frontend). `pnpm sidecar`
is `node scripts/sidecar.mjs`, which runs backend/agent/packaging/
build_sidecar.py with the agent venv's own Python. Before that
it was `pnpm build`, which built only the frontend and bundled WHATEVER
binary happened to be sitting in src-tauri/bin.

That cost a lab session on 2026-09-22. The agent had been changed to accept a
single base station; the app had not been re-frozen, so it still demanded two,
refused assisted flight and offered the barometer instead. Every flight that
day ran on a sensor with 72 cm of noise while the Lighthouse next to it was
good to 1.3 cm — and it read as a drone fault, not a build fault.

`pnpm app` does the same and then opens the result, which is the usual thing
to want after changing the agent.

The halves can still be built separately when that is what is wanted:
        pnpm sidecar        freeze the agent only (~25 s)
        pnpm build          frontend only

NO VIRTUALENV ACTIVATION IS NEEDED for any of this. sidecar.mjs runs the
venv's Python by path (bin/python or Scripts/python.exe) and never reads the
caller's PATH. The agent's
CLI is the same: `./cropwatcher` at the repo root execs the venv's executable
directly, so `source .venv/bin/activate` is not part of any workflow here.
Rust lives in ~/.cargo/bin, which a login shell may not have on PATH.


DECISIONS

- The sidecar is spawned from RUST, never from the webview. Granting the
  frontend shell:allow-execute would let any script in the window start a
  process; the window holds no such permission, and the only binary this app can
  launch is the one compiled into externalBin.
- A control token is generated per launch (Uuid::new_v4), passed to the agent in
  its environment and to the window through the `agent_token` command. See
  ../backend/agent-api.txt.
- Native work the webview cannot do lives in Rust commands: the control token,
  stop_motors, and Drone Wi-Fi's network scan and secure store (src/wifi/,
  see drone-wifi.txt). The Wi-Fi password is pushed to the agent FROM RUST, so
  it is never read back into the window.
- THE APP IS NOT CODE-SIGNED (ad-hoc locally; no signing step in CI). Every
  build is a new app to the macOS Keychain, so Drone Wi-Fi's saved password
  prompts once per build (drone-wifi.txt). A Developer ID would end that.
- The Supabase project URL and PUBLISHABLE key are compiled into lib.rs, with
  the environment able to override them. An installed .app is launched by Finder
  with no shell profile, so reading them from the environment alone gives an
  operator "sign-in is not configured" and no way to fix it. The SECRET key must
  never appear here — this binary ships inside an installer.
- One-file PyInstaller binary. A folder of loose libraries beside the app is
  worse to ship and to sign. It costs startup time — ~40 MB is unpacked on
  every launch, ~7 s to first answer on an M-series Mac and longer on an older
  Intel Mac — which the window and the verifier both wait out. Revisited
  2026-09-25 and kept: startup speed did not explain the Intel failure.
- ONE BUILD PATH AND ONE SETUP FOR EVERY OS, in Node and Python — never bash.
  pnpm runs package scripts through cmd.exe on Windows, so a script naming
  build_sidecar.sh failed there with "'..' is not recognized" on every release
  run. Node is already required (pnpm) and Python already required (the
  agent), so scripts/setup.mjs, desktop/scripts/*.mjs and build_sidecar.py
  run unchanged on macOS and Windows. Do not add a .sh or .ps1 to this path.
- NO DOCKER, for the app or the agent (asked 2026-09-25). Docker on macOS
  cannot reach USB, and an installer that first needs Docker Desktop is not
  one download.
- WHEN THE AGENT DIES, THE WINDOW SAYS WHY. lib.rs keeps the agent's newest
  error-looking line; on exit it composes one sentence (exit code + that
  line; a bind failure becomes "Port 8765 is already in use — another copy
  is running"), keeps it in state (`agent_exit`) and emits `agent-exit`. The
  "Not connected" banner shows it with the log path (`agent_log_path`,
  mirroring paths.py). Before, the reason went out as `agent-log` events that
  nothing listened to, and the operator read "Restart CropWatcher".
- THE WINDOW COMES BACK WHEN THE ICON IS CLICKED (macOS). lib.rs handles
  RunEvent::Reopen — the Dock or Launchpad icon clicked while running — and
  RunEvent::Ready by showing, un-minimising and focusing the main window, which
  also opens centred ("center": true). Tauri ignores Reopen by default, so a
  window that was hidden or never ordered front stayed invisible however often
  the icon was clicked: on an Intel Mac (2026-09-25) Launchpad gave a Dock icon
  and no window, while starting the binary from Terminal gave one.
- THE SHELL KEEPS ITS OWN LOG: logs/shell.log beside agent.log, capped at
  256 KB. Each launch and each Dock click records the window's visibility,
  position, size and display, before and after bringing it forward. A
  Launchpad launch sends stderr nowhere, so before this there was no evidence
  at all.
- A BUILD REFUSES TO RUN WHILE A COPY RUNS FROM THE BUILD FOLDER
  (desktop/scripts/refuse-if-running.mjs, first step of build:all). `pnpm tauri
  build` rewrites bundle/macos/CropWatcher.app in place — the copy `pnpm app`
  opens — and macOS can kill a program whose signed code changes under it. On
  2026-09-25 a copy running there stopped 24 s after a rebuild replaced it
  (unproven cause: no crash report; it may have been quit). It may be flying.
- A COMMAND THAT GETS NO ANSWER ASKS /health WHY (lib/agent.ts, no-cors, 2 s):
  nothing listening → "not running"; something listening → "running, but did
  not answer <path>". They used to be the same sentence.

  MEASURED FROM A REAL BUILD, 2026-09-22 (the previous figures — 27 MB and a
  30 MB .dmg — were stale and had been quoted in arguments since):

      Contents/MacOS/cropwatcher-agent   42 MB   the frozen agent
      Contents/MacOS/desktop            7.5 MB   the Rust shell + webview
      CropWatcher.app                    50 MB
      CropWatcher_0.1.0_aarch64.dmg      48 MB

  The growth is the AGENT, not the window: the frontend bundle is 647 KB
  (194 KB gzipped). Re-measure after adding a Python dependency — this is the
  number that decides whether a library is affordable, so a stale one argues
  the wrong way.
- The whole CLI is frozen, not just `serve`, so `cropwatcher-agent check` is
  available on a machine with no Python when a drone will not connect.
- Installed from a terminal, never downloaded (2026-09-25): each machine
  builds its own with scripts/install.mjs. See ../development/releases.txt
  for why the published installers stopped (the Windows one outgrew
  Supabase's 50 MB limit) and what the website still shows.


INVARIANTS

- Pass --exit-with-parent, and never rely on killing the child. A one-file
  PyInstaller binary is two processes. Measured from the built app:
  desktop(43661) -> bootloader(43666) -> python(43670), and the LAST one holds
  the port and the radio. Tauri kills only the bootloader; the Python process
  was re-parented to launchd, kept the radio, and the next launch reported "no
  drone found". Verified fixed on quit and on kill -9.
- The verifier's probe agent is isolated: verify_sidecar.py runs it
  with its own temporary data folder and CROPWATCHER_STANDBY=0 — without
  that, verifying on a developer's laptop restored their saved sign-in and
  could reach for the radio.
- The verifier's limits are ceilings for a hang, not estimates: 180 s to
  start, 240 s for `check`. An Intel Mac overran the old 20 s. The wait ends
  the moment the agent dies, with its own output, so a crash is never
  reported as a timeout.
- Closing stdin must stop the agent AND free its port, proven on every build
  by the verifier on every OS CI builds (it had only been measured on macOS).
  An agent that survives fails the build and is killed with its whole tree.
- LINUX INSTALLS PER USER, NO SUDO (install.mjs): the program in
  ~/.local/lib/cropwatcher (desktop + cropwatcher-agent side by side, as
  tauri-build leaves them in target/release — the app finds its sidecar
  there), a menu entry in $XDG_DATA_HOME/applications (Desktop Entry Spec
  1.5, validated in CI), the icon in hicolor, a `cropwatcher` link in
  ~/.local/bin (never over a file that is not ours). Not an AppImage (needs
  FUSE 2, absent on current Ubuntu) and not a .deb (needs sudo).
- THE WI-FI PASSWORD STORE ON LINUX IS SECRET SERVICE (keyring
  sync-secret-service + crypto-rust, Cargo.toml). With no Linux feature
  keyring 3 uses its MOCK store: the password "saved" and was gone at the next
  launch, silently. Needs libdbus-1 headers to build; without a keyring
  daemon a save fails with a message.
- LINUX PYTHON NEEDS ITS SHARED LIBRARY for PyInstaller. Ubuntu packages it
  apart (libpython3.X) and reports Py_ENABLE_SHARED=1 without it; setup.mjs
  checks the file at LIBDIR/INSTSONAME, and ensurepip (python3.X-venv).
- INTEL MACS NEED A PREBUILT cryptography (pyproject: >=46,<49 on macOS
  x86_64). cryptography 49+ ships macOS wheels for Apple silicon only, so on
  Intel pip compiled it against Homebrew's OpenSSL; the frozen agent then held
  two libssl.3.dylib under one file name, kept Python's older one, and could
  not import cryptography ("Symbol not found: _SSL_get0_group_name"). Since
  `supabase` needs it (supabase-auth → pyjwt[crypto]), no sign-in could start —
  on the Intel Mac, 2026-09-25, while the M4 and Windows signed in. setup.mjs
  installs with --only-binary=cryptography so a missing wheel fails the
  install instead.
- EVERY BUILD PROVES ITS LAZY IMPORTS LOAD: `cropwatcher-agent selftest`
  imports each library the agent loads only on demand (SELFTEST_MODULES in
  cli.py), and verify_sidecar.py runs it offline. Add a module there when new
  code imports a third-party library inside a function.
- CI SIGNS IN FOR REAL on every machine (packaging/check_sign_in.py): a
  probe account that cannot exist must get the agent's own 409 refusal —
  proof the client loaded and Supabase was reached. Run it by hand against an
  installed app when a machine cannot sign in.
- The Python that freezes the agent must be the same CPU as Rust's target.
  build_sidecar.py and setup.mjs both refuse a mismatch: an x86_64 Python
  under Rosetta on Apple silicon would ship an Intel agent named for arm64.
- Verify the frozen binary, not the build. A binary missing libusb builds,
  launches and serves /health; it fails only when a radio is plugged in.
  verify_sidecar.py asserts cflib enumerated USB ("Looking for devices") and
  that no bundling error appeared — "no drone found" is the CORRECT answer with
  no dongle. Exit codes cannot tell these apart.
- uvicorn's protocol modules are hidden imports; it selects them by string name,
  so nothing imports them statically and the binary otherwise cannot upgrade a
  WebSocket.
- A probe WebSocket key must be exactly 16 bytes (RFC 6455). A 17-byte key gets
  a 400 indistinguishable from "websockets not bundled" — that cost a build to
  tell apart. verify_sidecar.py probes /ws/live; rename the socket and this
  check must be renamed with it.
- Closing the window ends the session (land, close the flight, let the upload
  finish) rather than vanishing mid-flight. The agent's own dead-man landing
  stays as the net beneath that.
- Neither half cross-compiles: each OS and CPU builds its own. CI proves the
  install on macos-latest (Apple silicon), macos-15-intel and windows-latest.
