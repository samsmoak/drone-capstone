RLS AND GRANTS — authorization, enforced by the database
========================================================

WHAT IT IS

Every table has row-level security, and every client — the web app, the desktop
agent, a curl command — acts as a real account under it. Client-side role checks
exist only for what they show; the database is the gate.

The app is publicly reachable and commands a physical drone, so the rule is
fail-closed: no policy means no access.

THE CHECK

rls_check.py signs in as a real operator and asserts BOTH directions — what must
be allowed and what must be refused. It creates and deletes its own rows, so it
is safe to run against hosted:

  SUPABASE_API=https://<ref>.supabase.co \
  SUPABASE_ANON=<publishable key> SUPABASE_SERVICE=<secret key> \
  CHECK_EMAIL=<operator email> CHECK_PASSWORD=<password> \
  python backend/supabase/checks/rls_check.py

INVARIANTS

- A POLICY WITHOUT A GRANT IS A 403. They are separate systems: the policy says
  which rows, the grant says whether the role may touch the table at all. The
  drones insert policy looked complete and every insert failed with "permission
  denied" — migration 0004 had revoked the grant. Add both, together.
- A GRANT WITHOUT A POLICY IS A SILENT HOLE waiting for someone to add a policy.
  audit_events carried an UPDATE grant no policy used; 0006 revokes update and
  delete explicitly so the append-only rule cannot be undone by accident.
- The agent NEVER carries the service-role key. It ships inside a desktop
  installer, so that key would hand every downloader unrestricted access and
  bypass every policy. It signs in as a real operator with the publishable key
  and acts as `authenticated`.
- Authorization is enforced server-side on every request. A client-side role
  check is UX.
- HOSTED AND LOCAL DO NOT START THE SAME. The hosted project grants
  `authenticated` ALL privileges on `public` by default; a local `supabase
  start` does not. Migration 0004 revokes and re-grants explicitly so the two
  agree. ADD A TABLE AND YOU MUST CHECK ITS GRANTS ON THE HOSTED PROJECT, not
  only locally — locally it will look correct while hosted silently allows more.
- A SECURITY TEST THAT ONLY CHECKS FOR DENIAL PROVES NOTHING. Confirm the
  permitted path works in the same test, or a missing grant is indistinguishable
  from a working policy: both deny, for opposite reasons, and only one is what
  you wanted.
