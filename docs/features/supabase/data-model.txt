DATA MODEL — the tables and what ties them together
===================================================

WHAT IT IS

One Postgres schema in Supabase, written by the agent on the operator's laptop
and read by the web dashboard. Nothing is written by the browser except mission
plans.

THE TABLES

  profiles      one row per account, created by the handle_new_user trigger,
                carrying the role. See accounts-and-roles.txt.
  drones        name, uri, and HARDWARE_ID — unique, "cf-<hex of cpu.id0..2>".
                This is what ties sensor and flight data to the machine that
                produced it when two people fly two drones.
  sessions      one operation: who, which drone, which mode, when it started
                and ended. operator_email and operator_name: who ran it,
                STAMPED BY THE DATABASE from profiles on every insert and
                update (trigger stamp_session_owner, migration 20261009000015),
                so a client can neither set nor change them, and the web shows
                every owner while profiles stay "read own".
  pipeline_results  ONE ROW PER PROCESSED FLIGHT (migration 20261009000016):
                the whole result.json — verdicts per point, the cleaner's
                flags [index, column, kind, reason], the tracks (observed and
                expected per reading), the blocks, every frame's enhanced
                copy, quality and label — plus findings_count and
                worst_severity. Replaced when the flight is processed again.
  pipeline_findings  ONE ROW PER FINDING: signal, severity, title, sentence,
                start/end, observed/expected/delta/z, point_ids, position,
                evidence_frames, image_support. The id is made on the laptop
                from the flight and the stretch, so a re-process upserts.
                Both: signed-in read; operators write (findings also delete —
                a re-process retracts what it no longer finds); anon nothing.
                Proof: backend/supabase/checks/results_check.py (11 checks).
  session_samples  the session's own vitals, one a second, flying or not:
                PRIMARY KEY (session_id, seq), telemetry's column names where
                they mean the same, `positioned`, and every stream variable in
                `values`. Signed-in read; insert by an operator for their own
                session only; append-only (migration 20261006000013; its grants —
                select, insert to authenticated, as telemetry — are 0014). Read by
                /app/sessions (../frontend/operator-dashboard.txt).
  flights       belongs to a session. Carries mode, program, outcome,
                abort_reason, ground_z_m, ambient_start, temp_unit, csv_path,
                and operator_email / operator_name stamped like sessions' from
                created_by — or, when that is empty, the session's operator.
  telemetry     one row per 10 Hz sample, UNIQUE (flight_id, index), with the
                position, attitude, motion, power and environment columns the
                stream publishes.
  audit_events  append-only history. No foreign keys — see ../backend/audit-trail.txt
  zones         the greenhouse areas a mission visits.
  missions      a queued plan, claimed by the agent through claim_mission().
  predictions   zone-level crop-health estimates.
  projects      the public portfolio: slug, title, summary, cover, a BlockNote
                write-up, draft/published. See ../frontend/portfolio.txt.
  team_members  people on /team and beside projects: name, role, photo,
                website, email, display order.
  project_members  who worked on which project, in order.
  gallery_albums   public albums: slug, title, category, cover, draft/published.
  gallery_items    an album's photos (storage URL + width/height) and videos
                   (YouTube links), in order. See ../frontend/gallery.txt.
  site_pages       per-page wording overrides (JSON), keyed by page. See
                   ../frontend/site-pages-and-views.txt.


DECISIONS

- Ids are generated on the laptop, not by the database, so a flight that
  happened offline already has the id its telemetry references.
- telemetry is unique on (flight_id, index) rather than on a timestamp: it makes
  re-sending free, and resuming an upload a matter of asking for the highest
  index the server holds.
- The ambient temperature unit is stored in the row, not converted at write
  time — the operator chose it at launch and the record should say which.
- claim_mission(uuid, text) is a function, not an UPDATE from the client, so
  claiming is atomic and a second agent cannot claim the same mission.


INVARIANTS

- flights.ground_z_m is the floor captured at takeoff, and telemetry z is
  ALREADY relative to it. Lighthouse z = 0 is not the floor: measured floor
  level ranged 0.85–1.40 m in the same room across runs. Subtracting ground_z_m
  again on read (the web did this) shows heights that are wrong by the floor
  offset.
- After applying a migration by hand, reload PostgREST's schema cache
  (`notify pgrst, 'reload schema'`). Until then new tables answer 404
  PGRST205 "could not find the table" even though they exist.
- Never run `supabase db reset` against the hosted project. It drops
  everything. `supabase db push` is the one that applies migrations there.
- The LOCAL database carries synthetic rows added while the pages were built:
  flights aaaaaaaa-…-0001 to -0004, their telemetry, 8 predictions and a few
  missions. Local only — they are not on the hosted project, and a local
  `supabase db reset` clears them. Do not read a local row count as real data.
- Flight data never goes in git.

- telemetry.point_id (migration 20260928000012_telemetry_point_id.sql, text,
  indexed with flight_id where set): the inspection point a reading was taken
  at. NOT YET APPLIED to the hosted project — `cd backend && supabase db push`.
