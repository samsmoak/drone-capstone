1. WHAT IT IS
--------------------------------------------------------------------------------
The session takes a saved mission (floor-plans.txt), refuses anything unsafe
before a motor turns, arms the MANUAL FLIGHT SYSTEM (flight/manual.py — the
tuned 50 Hz loop that flies Manual mode) and hands it, with the mission, to the
MISSION CONTROLLER. The mission controller flies the mission by giving that
system goals — hold_at() to take off, fly_to() for each inspection point,
land() at the end — and holds at each point while the readings and frames are
stamped with its id. It decides where next and when; never how.

3. DECISIONS
--------------------------------------------------------------------------------
• ONE WAY OF FLYING. The old mission runner (flight/missions.py execute())
  flew with the firmware's go_to — a second control path with none of manual
  flight's tuning. It is deleted. A mission goes through fly_to(), which adds
  no control law: it moves the one commanded point at the arrow keys' eased
  speed (0.20 m/s), on the same 30 cm leash, slowing so it arrives without
  overshoot — the approach profile the height goal uses.
• KEYS ALWAYS WIN. Any held key cancels every goal at the top of the tick and
  sets operator_override; the mission ends INTERRUPTED and the drone is the
  operator's, as in Manual — the arrows away from them, or in the room's
  directions, never along the nose (../backend/manual-control.txt). fly_to's
  own velocity is in the room's frame and no heading bends it.
• THE MISSION'S SPEED (2026-10-01): MissionFlight.fly_to takes an optional
  speed_m_s, and the controller passes the mission's (floor-plans.txt, ONE
  SPEED PER MISSION). Optional, so nothing written against the seam before
  breaks — but it IS a change to THE SPEC's seam, which is Hannah's to know
  about (../../handoffs/sprint-1/undone/mission-controller.txt).
• THE HEARTBEAT STAYS WITH THE APP. The controller never calls heartbeat(): if
  the window goes quiet the drone lands, mission or not.
• EVERY REFUSAL BEFORE ANYTHING ARMS: Auto, assisted, checks passed, the
  mission valid in its room, the mission valid AGAIN FROM WHERE THE DRONE IS,
  the battery budget for that path, and the controller BUILT.
  tests/mission/test_session_missions.py proves each leaves the motors
  untouched.
• THE FLIGHT STARTS FROM THE DRONE (2026-09-29; it was "within 0.30 m of
  home, or refused"). The owner's ask: a saved mission is flown later, from
  wherever the drone was set down, and the drone is the start. The session
  applies Mission.from_start(position): the start moves to the drone, the
  POINTS DO NOT (they mark equipment — shifting them would put P2 beside the
  wrong pump), points after an END POINT are dropped, and the result is
  validated like any mission: the drone inside the fence and clear of
  obstacles, the leg to P1 and back clear. That from-start mission is what is
  handed to the controller, kept with the flight and read by the pipeline.
  GET /missions/{id}/from-drone runs the same function for ② Check.
  SINCE 2026-10-01 it is THE PLAN THAT WILL FLY (floor-plans.txt, fit.py):
  from the drone AND fitted to the flyable space — points outside it moved
  to the nearest fine spot, named, and kept with the flight as "moves".
• THE ROOM'S FENCE FLIES WITH IT: the in-flight guard lands the drone outside
  the room's own polygon, not the ±2 m square Manual uses.
• The flight is named "mission:<id>@r<revision>" and the exact plan flown —
  from its real start, end point applied — is copied to
  sessions/<id>/missions/<flight id>.json; the pipeline reads it.
• The base-station geometry is NOT re-checked at Start: if the stations moved
  since the room was drawn, absolute positions mean something else. That
  needs the room's geometry fingerprint (floor-plans.txt, NOT BUILT).
• POINT_ID UPLOAD FALLBACK: a batch with no point id sends no point_id key, and
  a batch the database refuses over the column is re-sent without it (the CSV
  keeps it). One mission flight before the migration can never stall the
  upload queue for every flight behind it (syncer aborts a pass on one error).

--------------------------------------------------------------------------------
4. INVARIANTS
--------------------------------------------------------------------------------
• current_point_id is set ONLY while HOLDING. A reading taken in transit must
  never carry a point id, or the pipeline analyses travel as equipment.
• The controller uses MissionFlight only — never arm, start, stop,
  emergency_stop or heartbeat. tests/mission/test_boundaries.py checks the
  manual system satisfies it.
• Apply migration 20260928000012 before flying missions: until then the
  inspection point reaches the CSV but not the database.

DECISIONS
• EVENTS ARE QUEUED, THEN DELIVERED IN ORDER. One lock guards the state
  machine and every command given to the flight; events are queued under it
  and delivered with no lock held, by one caller at a time. Delivering right
  after unlocking let an abort()'s ABORTED reach the listener before a tick's
  POINT_COMPLETE — the ordering E1 forbids. A test races the two.
• WHERE THE SPEC IS SILENT, and what this does (THE SPEC itself is Hannah's
  and Yordi's to settle, so none of this is written into their ticket):
    hold_at() refused at start()   FAILED, and start() raises MissionError
    no commanded point at T6       the exception path: land, FAILED, named
    tick() before start()          nothing
    start() after abort()          raises, commands nothing
    LANDING                        no timeout: the manual landing always ends
• THE SIMULATOR FLIES IN THREE DIMENSIONS, in the estimator's frame (the
  floor is ground_z). THE SPEC's arrival (drift_m ≤ ARRIVE_M) is x-y only;
  the height is the flight system's goal. The scenarios prove both put the
  drone at the point while it is stamped, and the report shows the height
  error beside the x-y drift (stateEstimate.z − posCtl.targetZ: no floor
  needed). ARRIVE_M is suggested from x-y only, as the controller uses it.
• THE REPORT READS ONLY WHAT AN APP FLIGHT WRITES. `cropwatcher mission`
  (the terminal) writes no trace and no plan flown, and records under the
  flight id "cli" — the report says so and exits non-zero. Fly the lab rungs
  from the app.
• THE EVENTS' WORDS ARE THE OPERATOR'S COMMENTARY (2026-10-01, Samuel's
  ask): the session puts each event's detail in the Command log, so each
  says what comes next — "P1 complete — flying to P2", "P3 reached — the
  last point", "…; landing now" / "…; returning to the start", "Returning
  over the start, then landing". Words only: THE SPEC's kinds and order are
  unchanged, and it has no event where a landing after a return begins, so
  RETURNING announces it. test_mission_sim.py pins the words.
• THE MISSION'S SPEED (2026-10-01, with PR #93 merged into this branch):
  each leg is flown with fly_to(…, speed_m_s=the mission's Steady/Normal/
  Brisk), and T8's timeout is the leg at THAT speed + TRANSIT_MARGIN_S — a
  Steady mission is not timed out as if Brisk. test_controller and
  test_mission_sim pin both.
• ONE PLACE KNOWS WHERE A FLIGHT'S FILES ARE: the report finds the flight
  CSV and session folder through pipeline/sources.py LocalFlightSource (its
  _find_csv, _find_session), the trace beside the CSV, the plan flown in the
  session's missions/ folder.

FOUND, NOT FIXED — outside both tickets; Samuel's call
• `cropwatcher mission` DOES check BUILT (cli.py, since 0ca26ba, 2026-09-28)
  — so with BUILT = True on this branch it flies the drone, as designed.
  (This line said "no BUILT check" until 2026-10-01: wrong, corrected after
  reading the code.) What is still true: it writes no trace and no plan
  flown, so the report cannot read its flights — fly the rungs from the app.
• T8's timeout treats a 3-D leg as flown at MOVE_SPEED_M_S (0.20 m/s); the
  height moves at CLIMB_RATE_M_S (0.15 m/s). A 0.7 m climb takes ~4.7 s
  against 3.5 s + TRANSIT_MARGIN_S — the margin absorbs it.
  Mission.estimated_duration_s already takes the longer of the two.
• Mission.estimated_duration_s(settle_s=1.0) is a copy of SETTLE_S.
• In simulation (lag 0.5 s, a guess) the test room's 3-point mission flies
  1.7 s longer than its estimate with return_to_start, 1.2 s without. The
  estimate is the battery budget; the lab will say by how much for real.
