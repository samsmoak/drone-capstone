--------------------------------------------------------------------------------
1. WHAT IT IS
--------------------------------------------------------------------------------
The session takes a saved mission (floor-plans.txt), refuses anything unsafe
before a motor turns, arms the MANUAL FLIGHT SYSTEM (flight/manual.py — the
tuned 50 Hz loop that flies Manual mode) and hands it, with the mission, to the
MISSION CONTROLLER. The mission controller flies the mission by giving that
system goals — hold_at() to take off, fly_to() for each inspection point,
land() at the end — and holds at each point while the readings and frames are
stamped with its id. It decides where next and when; never how.

3. DECISIONS
--------------------------------------------------------------------------------
• ONE WAY OF FLYING. The old mission runner (flight/missions.py execute())
  flew with the firmware's go_to — a second control path with none of manual
  flight's tuning. It is deleted. A mission goes through fly_to(), which adds
  no control law: it moves the one commanded point at the arrow keys' eased
  speed (0.20 m/s), on the same 30 cm leash, slowing so it arrives without
  overshoot — the approach profile the height goal uses.
• KEYS ALWAYS WIN. Any held key cancels every goal at the top of the tick and
  sets operator_override; the mission ends INTERRUPTED and the drone is the
  operator's, as in Manual.
• THE HEARTBEAT STAYS WITH THE APP. The controller never calls heartbeat(): if
  the window goes quiet the drone lands, mission or not.
• EVERY REFUSAL BEFORE ANYTHING ARMS: Auto, assisted, checks passed, the
  mission valid in its room, the mission valid AGAIN FROM WHERE THE DRONE IS,
  the battery budget for that path, and the controller BUILT.
  tests/mission/test_session_missions.py proves each leaves the motors
  untouched.
• THE FLIGHT STARTS FROM THE DRONE (2026-09-29; it was "within 0.30 m of
  home, or refused"). The owner's ask: a saved mission is flown later, from
  wherever the drone was set down, and the drone is the start. The session
  applies Mission.from_start(position): the start moves to the drone, the
  POINTS DO NOT (they mark equipment — shifting them would put P2 beside the
  wrong pump), points after an END POINT are dropped, and the result is
  validated like any mission: the drone inside the fence and clear of
  obstacles, the leg to P1 and back clear. That from-start mission is what is
  handed to the controller, kept with the flight and read by the pipeline.
  GET /missions/{id}/from-drone runs the same function for ② Check.
• THE ROOM'S FENCE FLIES WITH IT: the in-flight guard lands the drone outside
  the room's own polygon, not the ±2 m square Manual uses.
• The flight is named "mission:<id>@r<revision>" and the exact plan flown —
  from its real start, end point applied — is copied to
  sessions/<id>/missions/<flight id>.json; the pipeline reads it.
• The base-station geometry is NOT re-checked at Start: if the stations moved
  since the room was drawn, absolute positions mean something else. That
  needs the room's geometry fingerprint (floor-plans.txt, NOT BUILT).
• POINT_ID UPLOAD FALLBACK: a batch with no point id sends no point_id key, and
  a batch the database refuses over the column is re-sent without it (the CSV
  keeps it). One mission flight before the migration can never stall the
  upload queue for every flight behind it (syncer aborts a pass on one error).

--------------------------------------------------------------------------------
4. INVARIANTS
--------------------------------------------------------------------------------
• current_point_id is set ONLY while HOLDING. A reading taken in transit must
  never carry a point id, or the pipeline analyses travel as equipment.
• The controller uses MissionFlight only — never arm, start, stop,
  emergency_stop or heartbeat. tests/mission/test_boundaries.py checks the
  manual system satisfies it.
• Apply migration 20260928000012 before flying missions: until then the
  inspection point reaches the CSV but not the database.
