SESSIONS AND MODES — who is flying, in which mode, and how it ends
==================================================================

WHAT IT IS

One state machine in the agent that owns everything an operation does: signing
in, connecting to the drone, running the checks, taking the operator's
confirmation, flying, and ending cleanly. The desktop window renders this state
and nothing else — it never decides what is allowed.


WHERE IT LIVES

  backend/agent/cropwatcher/session.py       the state machine
  backend/agent/cropwatcher/flight/link.py   DroneLink: the only radio chokepoint
  backend/agent/cropwatcher/api/rest.py      the commands that drive it
  backend/agent/tests/test_session.py


THE STATES

  signed_out            -> sign_in
  idle                  -> start           (signed in, no drone session)
  starting              -> checks running
  checks_failed         -> start again, or retry inside an open session
                           (only: no telemetry, sys.canfly = 0, or motors held)
  awaiting_confirmation -> confirm_area    (drone on the floor, area clear)
  ready                 -> health_test / run_program / arm_manual
                           or, when retry_required, only: retry
  busy                  -> land / emergency_stop
  ending                -> land if needed, close the flight, flush the upload

MODE is auto or manual, chosen in the desktop app's SIDEBAR, and DEFAULTS TO
MANUAL (Snapshot.mode). It cannot change while busy: swapping controller mid-air
would hand the drone to a different command source with no warning. (It sat in a
top bar until 2026-09-22; the window is a sidebar and a flight strip now — see
../desktop/pages-and-windows.txt.)

The default was AUTO until 2026-09-23, and that was the wrong way round for this
drone. Auto needs `assisted` — a position the drone can hold — and run_program
refuses without it (flight-safety.txt). Until a room's Lighthouse geometry is
measured every session comes back unassisted, so an Auto default opened the app
in the one mode that could not fly, and filtered the history to the mode the
operator was not using. Tests that exercise Auto now set the mode explicitly,
which is what a test about Auto should do anyway.

  auto    Hover test (rise, hold a steady height, land where it started)
  both    Battery & motor test (each motor on its own, then the battery under
          all four — the firmware's two health tests)
  manual  Start (props idle on the ground), then held keys fly it — or Hover,
          which rises to a height and holds it without W being held. Unlike the
          Auto hover test it needs no position estimate, so it works on the
          barometer. See manual-control.txt

Both modes run the same checks and take the same confirmation. When the checks
warn about positioning, the session is UNASSISTED (snapshot.assisted = False,
with unassisted_reason): confirm_area needs accept_unassisted = True, Auto
programs are refused, and Manual flies on barometer height hold (manual-control.txt).

A MANUAL FLIGHT THAT COMES DOWN GIVES THE SESSION BACK. However it ended — Land,
S to the floor, the heartbeat, a guard, Emergency stop — the watcher closes the
flight record and returns the session to READY, so End session and the mode
toggle work again. Before this a tumble left the app "busy" with no way out. A
low-battery landing goes further and ends the session.

AN ABNORMAL END NEEDS A RETRY. A guard abort, a tumble or an emergency stop (and
an Auto program that aborts or fails) sets retry_required. Nothing flies and no
test runs until Retry, which runs the exact path a new session takes — open the
link if it is closed, every check including the motors, then confirm the area
again — inside the SAME session: same id, same history, same audit trail. A
retry that fails leaves the session open in checks_failed with the link closed,
so a power-cycled drone gets a fresh link on the next Retry; Start is refused
while that session is open. A normal landing does not require a retry.

STAYING SIGNED IN. Signing in saves the Supabase refresh token in the app data
folder (session.json, mode 0600). At startup the agent restores it in the
background; an expired or revoked token is deleted and the sign-in form shows.
Signing out deletes it.


TURNING IT ON AND OFF

"Start session" is the single on switch for both modes; "End session" is the
single off switch. Ending always lands first if the drone is in the air, then
closes the flight row, writes the audit event and lets the upload finish.
Closing the window does the same thing rather than vanishing mid-flight.


STANDBY — THE DRONE CONNECTED WITH NO SESSION (2026-09-24)

Signed in and idle, the agent holds a link to the drone: vitals stream to every
page and the camera gets its Wi-Fi network (drone-wifi.txt), before any session.

  radio.state  off        signed out, or standby not started
               searching  no drone found yet; `message` says why
               connected  a link is open — vitals live, motors off
               paused     the operator pressed Disconnect (radio free for a tool)

It looks at sign-in and 2 s after any link closes (a session ending, the drone
dropping), then every 15 s while nothing is found. Home carries Connect /
Disconnect; POST /drone/connect and /drone/disconnect. CROPWATCHER_STANDBY=0
turns it off.

RESTART OVER THE RADIO (restart_drone). Between sessions only, the agent can
power-cycle the drone's electronics through its radio chip; standby waits 4 s
(RESTART_SETTLE_S — a connect while it boots blocks for its full timeout) and
reconnects. radio.state reads "restarting" meanwhile. It exists for the camera
(drone-wifi.txt): it is the one supported way to make the deck rejoin.

A session TAKES OVER the standby link rather than opening a second one — and
runs every check on it exactly as on a link it opened itself. When the session
ends the link closes as before and standby reconnects.


DECISIONS

- The agent, not the UI, owns what is allowed. A window can be refreshed,
  crashed or replaced; the drone's permission to fly must not depend on it.
- Sign-in is required before anything arms, because a flight with no name on it
  is not much of an audit trail (see audit-trail.txt).
- A low battery mid-flight ends the operation in BOTH modes: the guard lands the
  drone and the session ends itself, rather than returning to "ready" with a
  battery that cannot fly again.
- Endurance is reported at the start ("about N seconds of flying left") so the
  operator plans the flight instead of discovering the limit in the air.


INVARIANTS

- STANDBY NEVER ARMS. It opens the link, reads two params (hardware id,
  deck.bcAI) and publishes telemetry. No flight command runs without a session;
  can_fly stays false; a test pins that it does not even run the checks.
- A SESSION RECORDS ITS CAMERA. on_session_open / on_session_close start and
  stop the frame recording (desktop/camera.txt) in the session's own folder.
- STANDBY RECORDS NOTHING. Telemetry reaches a file only through a session's
  history, which exists only inside a session. Vitals before a session are
  shown, never stored.
- ONE LOCK OPENS AND CLOSES THE LINK (Session._link_lock), whoever does it —
  standby, start, retry, end, sign-out. A session starting while standby is
  mid-connect waits and inherits the link.
- A STANDBY LINK THAT DROPS IS CLOSED OFF CFLIB'S THREAD. cflib reports the loss
  on its own thread and closing the link inside that callback can deadlock it;
  the close is handed to another thread. A link a SESSION owns is not closed on
  loss — the flight guards own that — only the radio state is updated.
- A LINK CLOSING TELLS EVERYONE WHO CLAIMED IT WAS UP. The Wi-Fi state returns
  to "waiting" (drone-wifi.txt) and the window clears its vitals. Measured
  2026-09-24: with the battery flat, the Wi-Fi page read "Radio: no drone"
  beside "On VT Open WiFi", and the sensor pages would have kept saying "Live".

- Every command carries the control token (X-Agent-Token). The agent binds
  localhost, which keeps other machines out but not other programs or web pages
  on this one — and its API arms a drone.
- The radio scan is cached and never runs while busy. Scanning every 2 seconds
  from /status wedged the agent with [Errno 19] No such device; the window polls
  /health instead.
- The drone is identified by hardware id (cpu.id0..2 as "cf-<hex>"), so sensor
  and flight data tie to the machine that produced it even when two people fly
  two drones on different days.


AUTO: A MISSION (2026-09-28)

run_mission(mission_id, ambient) is Auto's second activity beside the hover
demo ("mission"). Every refusal comes before anything arms — Auto, assisted,
checks passed, the mission valid in its room, the battery budget, the drone
within 0.30 m of home, and the mission controller built — then the manual
flight system is armed with the room's fence as the guard's, and handed to the
mission controller (../missions/mission-controller.txt). The snapshot's
`mission` carries its progress to the app.
