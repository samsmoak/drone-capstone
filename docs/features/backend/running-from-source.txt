RUNNING THE AGENT FROM SOURCE — for working on flight code
==========================================================

WHAT IT IS

The desktop app bundles the flight agent as a frozen sidecar, so nobody who only
flies the drone ever starts it by hand. This is for developers: changing flight
code, running the tests, reading a trace, or bringing up a drone from a terminal.

It used to be a setup guide on the website (/setup/flight-agent). It moved here
because the website is for the people who fly the drone, and a second card on
/setup read like a second thing they had to install.


SET IT UP

On the laptop the Crazyradio is plugged into, from the repository root:

  node scripts/setup.mjs --dev

It checks Python 3.11+, Rust, pnpm and the native toolchain, creates
backend/agent/.venv (recreating one that cannot run here, or is for another
CPU), and installs the agent editable with its test tools and PyInstaller.
The same command on macOS and Windows. Then:

  cd backend/agent
  source .venv/bin/activate        (Windows PowerShell: .venv\Scripts\Activate.ps1)

Editable install: changes are live without reinstalling.

  cropwatcher serve                starts the local API on 127.0.0.1:8765
  pytest                           the gate — guards and checks need no drone
  pytest -k guard                  just the in-flight guards

Open http://127.0.0.1:8765/health to check it answers. Every command needs the
control token, even on localhost (agent-api.txt).


WHEN IT WILL NOT RUN

- No Crazyradio found
  Usually: another program holds the dongle, or the process cannot see it.
  Close cfclient and any script using the radio, re-plug the dongle.

- Linux: "Crazyradio found, but this user may not open it"
  Only root may open it until Bitcraze's udev rule is in place and the user
  is in its group (plugdev), after a fresh login. `node scripts/install.mjs`
  prints the exact rule and commands (scripts/lib/radio-access.mjs); the agent
  reads the device node /dev/bus/usb/BBB/DDD to tell (flight/radio.py).

- Windows: "Crazyradio found, but Windows has no driver" / "the wrong driver"
  cflib opens the radio through libusb0 on Windows, i.e. the libusb-win32
  driver, which Windows never installs itself. Zadig → Options → List All
  Devices → Crazyradio PA USB Dongle → libusb-win32 → Install (or Replace)
  Driver. WinUSB is the wrong one. flight/radio.py tells these apart by asking
  the bundled libusb-1.0 (which lists the dongle whatever its driver) and
  then libusb0 (which only sees it with the right one).

- The drone connects but the motors never spin
  Usually: a low-level setpoint earlier in the same power cycle still holds
  priority over the high-level commander. Call send_notify_setpoint_stop()
  first, or power-cycle the drone. takeoff() returns successfully either way,
  which is what makes this slow to spot. (CLAUDE.md flight invariant 2.)

- It refuses to arm and blames the battery
  Usually: the firmware supervisor will not arm below roughly 3.75 V. Charge
  it. Read sys.canfly rather than guessing a threshold. (Invariant 1.)


INVARIANTS

- Docker cannot reach USB on macOS: Docker Desktop runs a Linux VM with no USB
  passthrough. The agent runs bare in a venv. (This used to say "the
  Dockerfile is for CI and Linux teammates" — there is no Dockerfile in the
  repo, and there was none when it was written.)
- To build the frozen sidecar the desktop app ships: `cd desktop && pnpm
  sidecar` (backend/agent/packaging/build_sidecar.py). See
  ../desktop/desktop-app.txt.
