FLIGHT TUNING AND THE FLIGHT TRACE — why the drone bounced, and what changed
============================================================================

WHAT IT IS

Two things a manual flight now does: it tunes the firmware's height loop for
THIS drone before arming and restores it afterwards, and it records a 10 Hz
trace of what the controller asked for beside what the drone did.


THE EVIDENCE (lab traces, 2026-09-17, two barometer flights, 177 + 265 samples)

  Motors hammered      ~15% of samples had a motor pinned at 0 or full while
                       the drone was being commanded, cycling every 0.2–0.4 s.
                       That is the bounce the operator felt.
  Yaw spun             20–35 °/s throughout, a turn every 10–15 s. A saturated
                       motor has no authority left for yaw — and a spinning
                       drone re-aims "forward" every few seconds, which is why
                       forward, sideways and rotate seemed not to work.
  vz is noise on baro  At rest with motors off the vertical-speed estimate read
                       ±0.5–0.8 m/s. velCtlPid.vzKp (25) multiplies that
                       straight into thrust.
  Hover is not 36000   Unsaturated airborne motor output averaged 48,400 and
                       49,100. posCtlPid.thrustBase assumes 36,000 (a stock
                       2.1), leaving the integrator to find ~13,000 — wind-up,
                       then overshoot.

THE PROFILES

  every manual flight   stabilizer.controller = 1 (PID), thrustBase = 48500
  barometer flights     velCtlPid.vzKp ×0.40, velCtlPid.vzKi ×0.30,
                        posCtlPid.zKp ×0.75, posCtlPid.zKi ×0.50

THE CONTROLLER IS PINNED, AND THAT MATTERS MORE THAN THE GAINS. The lab drone
was found on 2026-09-21 running stabilizer.controller = 2 — Mellinger, a
trajectory controller that wants an excellent position estimate, lurches
without one, and reads NONE of the gains in this file. Every tuning run before
that date was writing parameters the active controller ignored, which is why
they changed nothing. It was a leftover in RAM (a battery swap put it back to
1), so nothing in this repo had set it — which is exactly why it is now pinned
at arm time and restored afterwards.

Values are SCALED FROM WHAT THE DRONE REPORTS, never assumed, and the exact
originals are written back when the flight ends. These are starting values from
two flights — refine them from the traces, they are not a finished tune.


THE TRACE

One row per telemetry sample: the keys held, the eased height target and climb
speed the agent commanded, the firmware's own target (posCtl.targetZ), the
barometer estimator's height and climb rate, thrust, attitude, gyro z, the four
motors, battery, pm.state, supervisor.info, base stations received, and the
tuning in force. The first diagnosis had to infer held keys from motion because
nothing recorded them; the second had to infer a locked supervisor the same way.


INVARIANTS

- THE FIRMWARE NEVER REBUILDS THE CONTROLLER BY ITSELF. stabilizer.c calls
  controllerInit() in exactly one place:

      if (controllerGetType() != controllerType) {
          controllerInit(controllerType);
          controllerType = controllerGetType();
      }

  and nowhere else — not on disarm, not when the supervisor stops the motors,
  not between flights. Stopping only zeroes the setpoint and cuts the motors.
  So EVERY PID INTEGRATOR SURVIVES from one flight to the next for as long as
  the drone stays powered, and a crash that saturated thrust for seconds hands
  its wind-up straight to the next takeoff. That is why a drone that crashed
  earlier in a session flies oddly afterwards while a freshly powered one does
  not.

  Writing the controller type it already holds changes nothing and re-inits
  nothing, which is what BASE_PROFILE used to do. Kind.REINIT now writes
  another valid type first, pauses long enough for the 1 kHz stabilizer task
  to see it (CONTROLLER_REINIT_PAUSE_S), then writes the wanted one. It runs
  before a flight, on the ground, with the setpoint at zero.

- THE DRONE CANNOT BE DISARMED FROM HERE on this firmware. cflib's
  send_arming_request falls back to a legacy path below CRTP 12 (this drone
  reports 10) and is silently ignored: measured 2026-09-22, supervisor.info
  did not move for disarm, re-arm, a stop setpoint, or a same-value controller
  write. Anything that depends on an arm/disarm cycle to clear firmware state
  will do nothing and report success.

- Read before write. A gain is scaled from the value the drone reports, so a
  re-tuned or newer firmware is never overwritten with a number from here.
- A parameter the firmware does not publish is skipped and logged, not guessed;
  a refused write leaves that value alone and the rest still apply.
- Format by the parameter's declared type, not by how the old value looked: a
  float gain reported as "2" must not have 1.5 rounded back to "2", and a
  uint16 refuses "48500.0".
- restore() writes back the exact originals and is safe to call twice. Writes
  are RAM-only, so a power cycle also restores the firmware defaults.
- Tuning is applied before the estimator switch, so the barometer ground is read
  under the gains the flight will use.

WHAT THE LAB SHOWED — the tuning flew, and did not fix it

Three barometer flights with these profiles, 2026-09-17 03:37–03:39:

  Still bang-bang   30–47 % of airborne motor samples pinned at 0 or 65,535;
                    logged thrust swung +324,720 to −180,446 within 300 ms.
                    One flight flipped (roll 175°).
  The estimate      At rest on the floor, props idling, stateEstimate.vz read
                    up to 1.8 m/s (sd 0.4–0.66). Barometer height wandered sd
                    0.05–0.14 m, a 0.2–0.43 m range over 3 s — correlated drift,
                    not white noise. In the air, ±4.7 m/s.
  No base stations  lighthouse.bsReceive 0 throughout.

Scaling the gains was not enough, because the input — the vertical speed the
barometer estimate reports — is mostly noise at any gain that holds height.

A HEIGHT HOLD IN THE AGENT WAS TRIED AND REJECTED (simulated, never flown).
The idea: the agent sends bounded, slew-limited thrust and closes the height
loop itself. Simulated against the measured noise, 10 Hz telemetry and 120 ms
of radio delay:

  perfect hover knowledge, measured noise   ±0.2 m (0.44 m peak-to-peak)
  hover off by 3 % (a minute of sag)         0.6 m swings, even with no noise
  hover off by 6 %                           1.5–2 m offsets
  automatic liftoff on the barometer         detected 0.8 s late; launched 5 m

The barometer reaches the agent too slowly and too noisily for any hold built
there to be steady. The on-board loop has the sensors at full rate; the agent
never will.

WHAT WILL MAKE IT STEADY

  Base stations seen       assisted flight: Kalman position, hover setpoints —
                           the path that is built and correct, and unchanged.
  A Flow deck v2 fitted    laser height + optical flow: steady height and
                           position with no base stations.
  Barometer only           will wander tens of centimetres however it is coded.
                           Treat it as flying by eye.
