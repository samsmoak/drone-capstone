OFFLINE SYNC — flying with no internet, and getting the data up anyway
======================================================================

WHAT IT IS

A flight is written to this laptop first and uploaded afterwards. A laptop with
no internet flies exactly as well as one with internet: records sit in a local
outbox until a sync succeeds and are deleted only once the server has them.

The laptop has to be the one that pushes — no server can reach into it. That is
the same constraint as the radio.


WHERE IT LIVES

  backend/agent/cropwatcher/sync/outbox.py   records waiting, one file each
  backend/agent/cropwatcher/sync/cloud.py    every call made to Supabase
  backend/agent/cropwatcher/sync/syncer.py   when and in what order
  backend/agent/cropwatcher/sync/samples.py  a session's samples.csv as rows
  backend/agent/cropwatcher/sync/results.py  a flight's result.json as rows
  backend/agent/tests/test_results_upload.py
  backend/agent/cropwatcher/paths.py         where the data dir is
  backend/agent/cropwatcher/telemetry/sinks.py  CSV first, then cloud
  backend/agent/tests/test_outbox.py, test_syncer.py


THE ORDER (records reference each other)

  audit events -> drones -> sessions -> flights -> telemetry rows -> CSV file
  -> camera frames -> session vitals (sync/samples.py, Kind.SAMPLES)
  -> pipeline results (LAST: sync/results.py, Kind.RESULTS)

Session vitals go last because their table (migration 20261006000013) may not
exist yet: until it does that step fails with "apply migration
20261006000013", and everything before it has already gone. One outbox record
per session, a cursor through samples.csv moved after each 500-row batch, sent
once the session has ended and every row is up.

Pipeline results go after them for the same reason (migration
20261009000016). `cropwatcher process --flight` queues one record per flight
once result.json is written (the agent wakes the syncer when a processing job
finishes); the syncer waits while the flight's own record is still pending,
then uploads the enhanced frames from a cursor (to flight-frames/<session>/
enhanced/<seq>.png, replacing), upserts pipeline_results on flight_id, upserts
pipeline_findings on their ids, and deletes the flight's findings the new
result no longer makes. Processing a flight again re-queues it, which resets
the cursor and replaces what was uploaded. Proved against the local stack
with the real client, 2026-10-09.

Audit events deliberately have NO foreign keys, so they can go first and never
wait for a flight row that may not exist yet.

The sync runs during a flight, when a flight ends, at sign-in, and every minute
while anything is unsent. The window shows what is pending and will not report
"all data synced" until the outbox is empty.


CSV AND SERVER-SIDE BACKFILL

Every row is appended to a CSV on this laptop as it arrives, flushed per row.
The same rows upload as database rows while online. If a flight ends with rows
still unsent, the gzipped CSV is uploaded to the private `flight-logs` bucket
and the server backfills the remainder from that one file, rather than the
laptop replaying thousands of inserts.

Measured, so nobody has to guess: 202 bytes per row, about 470 KB for a
full-battery flight, roughly 250 KB gzipped. One upload, not a cron job.


DECISIONS

- Ids are generated on the laptop, not by the database. A flight that happened
  offline already has the id its telemetry rows reference, so uploading later
  needs no translation and re-uploading changes nothing.
- Everything is idempotent: records upsert on their own id, telemetry upserts on
  (flight_id, index) with ignore-duplicates, and a CSV already in storage counts
  as success rather than an error.
- Resume asks the server for max_telemetry_index(flight_id) and continues from
  there, instead of re-sending from row zero.
- The agent signs in as a real operator account with the publishable key and
  acts as `authenticated` under RLS. It NEVER carries the service-role key: this
  code ships inside an installer, and that key would bypass every policy for
  everyone who downloads it.


INVARIANTS

- CAMERA FRAMES: ONE OUTBOX RECORD PER SESSION, WITH A CURSOR (Kind.FRAMES,
  camera/recording.py). The syncer uploads the frames frames.csv marks
  upload=1, advancing "uploaded_through" after each, so an interrupted pass
  resumes where it stopped; frames.csv goes last, once the session has ended,
  and only then is the record sent. Not one record per frame: this outbox never
  deletes a sent record, and that would be ~1,200 files per ten minutes.

- Write the CSV first, then upload. A local write cannot fail; a flight cannot
  be re-run (CLAUDE.md #6).
- Write to the APPLICATION DATA DIRECTORY, never a relative path. Inside a
  bundled .app the working directory is "/", where the write fails — paths.py
  exists for exactly this.
- Files are written atomically (temp file + rename), so a crash mid-write cannot
  leave a half-record.
- Sort the outbox by occurred_at, never by filename. Filenames are random UUIDs,
  so ordering by name replayed history in arbitrary order.
- Resolve type hints with get_type_hints(), not __annotations__. Under PEP 563
  the annotations are strings, so `index + 1` concatenated instead of adding and
  every resumed upload was wrong.
- Flight data never goes in git.

- telemetry.point_id (migration 20260928000012) may not exist on the database
  yet. A batch with no point id sends no point_id key; a batch refused over the
  column is re-sent without it (sync/cloud.py). One failed batch aborts a whole
  sync pass, so refusing would stall every flight and frame behind it.
