AGENT API — the local HTTP and WebSocket surface
================================================

WHAT IT IS

What the desktop window talks to. It binds 127.0.0.1 by default: it can arm a
real drone, so putting it on a network is a deliberate act — and even on
localhost every command needs the local control token, because any page the
operator has open can reach 127.0.0.1.

Served by `cropwatcher serve`. `python -m cropwatcher.api.rest` does nothing —
the module has no entry point.


WHERE IT LIVES

  backend/agent/cropwatcher/api/rest.py     routes, auth, the live socket
  backend/agent/cropwatcher/api/tokens.py   the control token
  backend/agent/cropwatcher/api/events.py   EventHub, the in-process fan-out
  backend/agent/cropwatcher/flight/manual.py  the 50 Hz loop
  backend/agent/tests/test_api.py


ENDPOINTS

  open, no token
    GET  /health                    liveness, for the window and /setup
    GET  /status                    state, mode, drone, sync summary

  token required (header X-Agent-Token)
    GET  /session                   the full session state
    POST /auth/sign-in              email + password -> operator
    POST /auth/sign-out
    POST /session/mode              {"mode": "auto" | "manual"}
    POST /session/start             connect + run the checks
    POST /session/confirm           the area is clear
    POST /session/prop-test         Start test
    POST /session/program           Hover test {height_m, hold_s, ambient}
    POST /session/manual/arm        props idle on the ground
    POST /session/land              graceful landing
    POST /session/emergency-stop    cut the motors
    POST /session/end               land if needed, close, flush
    POST /sync/now                  push whatever is waiting

  WS /ws/live
    first message {"type":"auth","token":...}; then out: telemetry (10 Hz),
    session, sync; in: {"type":"intent","keys":{...}} and heartbeats.


DECISIONS

- One token per launch, generated by the Tauri shell and handed to the agent in
  its environment, then to the window through the `agent_token` command. A page
  on the internet cannot know it, so it cannot fly the drone.
- The token goes in the FIRST WEBSOCKET MESSAGE, not the query string: a query
  string ends up in access logs, and this one grants control of a drone.
- CORS allows GET only, from a fixed origin list, so the dashboard can see
  whether the agent is running. Extend with CROPWATCHER_ALLOWED_ORIGINS; never
  with "*".
- POST /flight/mission and /preflight were REMOVED. They flew a drone with no
  authentication and bypassed the checks entirely.
- Health log lines are capped at 10 repetitions (QuietHealthFilter) — the window
  polls /health, and an endless identical log made the real events unreadable.
  The status colour still reflects the live answer, not the last logged one.


INVARIANTS

- NOTHING THAT TALKS TO THE RADIO MAY WAIT FOR EVER. cflib's
  SyncCrazyflie.open_link() waits on an Event with no timeout
  (syncCrazyflie.py: `self._connect_event.wait()`), so a radio unplugged
  mid-handshake blocks its caller permanently. DroneLink runs it on its own
  thread and gives up after CONNECT_TIMEOUT_S (20 s); a healthy connect
  measured 0.7 s to scan and about 2 s for the TOCs. On 2026-09-22 the
  un-timed version wedged the desktop app: the checks worker never returned
  and every later action refused with "Something is already running".

- A BUSY MESSAGE MUST NAME WHAT IS BUSY. The session records the running
  worker and when it started, so the refusal says which step is stuck, for how
  long, and that End session is the way out. "Something is already running" is
  true, unactionable, and indistinguishable from a bug.

- Localhost does not keep websites out, and WebSockets are not covered by CORS.
  The control token — not the bind address, not the origin — is what guards
  every command.
- /status must never scan the radio while a session is busy. Scanning every two
  seconds wedged the agent with [Errno 19] No such device. The scan is cached,
  locked, and skipped while busy.
- --exit-with-parent exits when stdin closes. A one-file PyInstaller binary is
  two processes; killing the child reaches only the bootloader, and the real
  Python process keeps the radio. See ../desktop/desktop-app.txt.
