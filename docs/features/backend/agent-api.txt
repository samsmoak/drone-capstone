AGENT API — the local HTTP and WebSocket surface
================================================

WHAT IT IS

What the desktop window talks to. It binds 127.0.0.1 by default: it can arm a
real drone, so putting it on a network is a deliberate act — and even on
localhost every command needs the local control token, because any page the
operator has open can reach 127.0.0.1.

Served by `cropwatcher serve`. `python -m cropwatcher.api.rest` does nothing —
the module has no entry point.


WHERE IT LIVES

  backend/agent/cropwatcher/api/rest.py     routes, auth, the live socket
  backend/agent/cropwatcher/api/tokens.py   the control token
  backend/agent/cropwatcher/api/events.py   EventHub, the in-process fan-out
  backend/agent/cropwatcher/flight/manual.py  the 50 Hz loop
  backend/agent/tests/test_api.py

  WS /ws/live
    first message {"type":"auth","token":...}; then out: telemetry (10 Hz),
    session, sync, camera_wifi; in: {"type":"intent","keys":{...}} and heartbeats.


DECISIONS

- One token per launch, generated by the Tauri shell and handed to the agent in
  its environment, then to the window through the `agent_token` command. A page
  on the internet cannot know it, so it cannot fly the drone.
- The token goes in the FIRST WEBSOCKET MESSAGE, not the query string: a query
  string ends up in access logs, and this one grants control of a drone.
- CORS is decided per origin (LocalCORS, rest.py): the desktop window's
  origins (tauri://localhost, http://tauri.localhost, the dev server) may GET
  and POST; website origins may GET only, so the dashboard can see whether the
  agent is running; anything else gets no CORS headers. Extend the website
  list with CROPWATCHER_ALLOWED_ORIGINS; never with "*". (Until 2026-09-25
  this said "GET only" for everyone — it had drifted: GET-only broke every
  button in the window, and the code had long since split it.)
- EVERY REFUSED PREFLIGHT IS LOGGED — origin, method, path, reason — once per
  origin and reason, capped at 50. A page whose preflight is refused sees only
  "could not reach the agent", the same words as an agent that is not
  running; the agent's log is the one place the difference is written down.
- POST /flight/mission and /preflight were REMOVED. They flew a drone with no
  authentication and bypassed the checks entirely.
- Health log lines are capped at 10 repetitions (QuietHealthFilter) — the window
  polls /health, and an endless identical log made the real events unreadable.
  The status colour still reflects the live answer, not the last logged one.


INVARIANTS

- GET /camera carries `connecting` — true while the agent is working towards a
  picture (the deck joining or rejoining, or the camera reconnecting to a
  joined deck); the window shows a spinner and the reason, not "no signal".
- GET /camera's reason names the drone first. With no frames AND no radio link
  it says the drone is not connected (off, flat battery) rather than a network
  theory about an address the drone may no longer hold.
- CROPWATCHER_STANDBY=0 stops the agent holding the drone between sessions. The
  API tests set it: a background radio loop would race every test.

- NOTHING THAT TALKS TO THE RADIO MAY WAIT FOR EVER. cflib's
  SyncCrazyflie.open_link() waits on an Event with no timeout
  (syncCrazyflie.py: `self._connect_event.wait()`), so a radio unplugged
  mid-handshake blocks its caller permanently. DroneLink runs it on its own
  thread and gives up after CONNECT_TIMEOUT_S (20 s); a healthy connect
  measured 0.7 s to scan and about 2 s for the TOCs. On 2026-09-22 the
  un-timed version wedged the desktop app: the checks worker never returned
  and every later action refused with "Something is already running".

- A BUSY MESSAGE MUST NAME WHAT IS BUSY. The session records the running
  worker and when it started, so the refusal says which step is stuck, for how
  long, and that End session is the way out. "Something is already running" is
  true, unactionable, and indistinguishable from a bug.

- Localhost does not keep websites out, and WebSockets are not covered by CORS.
  The control token — not the bind address, not the origin — is what guards
  every command.
- /status must never scan the radio while a session is busy. Scanning every two
  seconds wedged the agent with [Errno 19] No such device. The scan is cached,
  locked, and skipped while busy.
- --exit-with-parent exits when stdin closes. A one-file PyInstaller binary is
  two processes; killing the child reaches only the bootloader, and the real
  Python process keeps the radio. See ../desktop/desktop-app.txt. The
  verifier now proves it on every build, per OS — but only with no session
  open, which is why it passed on the build below.
- EVERY SHUTDOWN IS BOUNDED: 20 s (SHUTDOWN_DEADLINE_S), then os._exit(1)
  whatever is still running. Noticing the parent is gone is half of it; the
  exit must not wait on session.end. On 2026-09-30 the watchdog fired, then
  session.end blocked on a Wi-Fi link to a drone silent for 3.7 h, and the
  agent held the radio and port 8765 for 9 h — refusing SIGTERM, since the
  lifespan shutdown calls the same session.end — until killed by hand; the
  next launch and install.mjs both found it running. arm_exit_deadline covers
  the watchdog and the lifespan (SIGTERM, Ctrl+C; armed only by `serve`, so a
  TestClient never exits the test run). 20 s sits above the longest honest
  landing (End session's 15 s wait) and below verify_sidecar's 30 s. uvicorn
  gets timeout_graceful_shutdown=5 — its default waits forever on an open
  WebSocket before the lifespan shutdown even starts.
- Once the parent is gone, log to the file only. Handlers write to stderr
  first (cli.py); with no reader a write there can block holding the handler
  lock and freeze every thread that logs — the 9 h agent's log stopped four
  minutes after the app closed. The watchdog detaches console handlers.
- /health must stay unauthenticated and cheap. The window's no-cors probe
  asks it whether ANYTHING is listening after a command got no answer, to
  tell "not running" from "running but this request failed".


ROOMS, MISSIONS AND FLYING ONE (2026-09-28)

  GET  /plan/limits                  the room's map and the editor's limits
  GET  /rooms, /rooms/{id}           with problems and valid
  POST /rooms, /rooms/{id}/delete    save; delete (409 while missions use it)
  GET  /missions, /missions/{id}     with problems, valid, path length, time
  POST /missions, /missions/{id}/delete   save (422 in words with no inspection
                                     point, or before its room is saved)
  POST /missions/validate            a draft {mission, room?} — the agent's check
  GET  /missions/{id}/from-drone     the mission checked from the drone's own
                                     position (its start), for ② Check —
                                     {position | null, mission view}
  POST /session/mission              {mission_id, ambient}: fly it, from where
                                     the drone is; every refusal a 409,
                                     before anything arms

THE DATA PIPELINE (2026-09-29)

  POST /session/processing           {on}: the DPP switch for this session
  GET  /flights/{id}/result          results/<id>/result.json and its job; a
                                     404 in words while there is none yet
  POST /flights/{id}/process         process a recorded flight now

A flight id goes into a path and onto a command line: 1–64 of [A-Za-z0-9_-]
(processing.FLIGHT_ID), anything else a 404.

Writes are POST, not PUT or DELETE: LocalCORS allows the window GET and POST
only, and widening that for a verb name is not worth it. A plan that cannot be
read is a 422 in words; a missing one a 404.
