# {{PROJECT}} — docs router

**Read this first.** One line per doc. Match the work you are about to do against
it, open that entry in full, then walk outward along its `RELATED` edges instead
of guessing which neighbours matter.

This router is also the **feature registry**: before building, find the feature
here to decide "new, or an addition to something that exists". An addition
inherits that doc's decisions, vocabulary and invariants.

Generated by the feature-kit on {{DATE}}. Edit freely — the kit never overwrites
an existing file.

## How the docs work

- **One doc per feature**, in `features/` (group by area/workspace once there are
  more than a handful). A feature that outgrows one screen becomes a folder with a
  `README.txt` index and one file per sub-feature.
- **Rules every screen obeys** → `design/`. **Technical rules cutting across
  features** (units, data access, authorization) → `platform/`.
- **Every doc opens with STATUS** — state per surface (backend / app / web / …),
  each claim verified against the code, with a `Last verified: YYYY-MM-DD` line.
  An undated status is worse than none; never verified says `NOT VERIFIED`.
- **Template:** `_templates/feature.txt`.
- **Edges** (in each doc's `RELATED` section, one clause saying what flows
  across), always written in BOTH docs in the same pass:

| edge | inverse | meaning |
|---|---|---|
| `depends-on` | `consumed-by` | one relies on the other's behaviour |
| `shares-data-with` | itself | same data, different purposes |
| `copied-from` | `copied-to` | one was built by adapting the other (`/copy-adapt`) |

- **Health:** `python3 docs/graph_check.py` computes it from the docs and git;
  `GRAPH_STATE.txt` records what is out of sync and what that blocks.
- **Project profile:** `PROJECT_PROFILE.txt` — repos, roles, the bridge between
  them, the call chain, gates, commit identity, deploy path.
